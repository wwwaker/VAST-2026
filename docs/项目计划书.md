# 多智能体系统异常行为可视分析项目计划书

**项目定位：**面向课程展示与 IEEE VAST Challenge 2026 Design Challenge 的可运行可视分析原型  
**数据范围：**VAST Challenge 2026 MC1、MC2，以及项目自建多智能体运行数据  
**计划版本：**1.2（补充 MC1 双声道、主题 token、回放边界与状态指示）  
**编制日期：**2026-11-04  
**版本说明：**1.2 相对 1.1 不改技术路线，只补齐可验收细节：MC1 消息与内心审议的对照、图表颜色必须来自主题 token、回放遮蔽的作用边界、章节导航与自由探索的状态指示、MC1 时间排序键的语义，以及键盘验收范围；工期仅作参考。

## 1. 项目摘要

本项目拟开发一套面向多智能体系统（Multi-Agent System, MAS）的可视分析原型，支持研究人员从大规模事件日志中理解系统构成、重建关键行为链、比较实际行为与历史基线，并检查异常判断所依据的证据。原型将使用 VAST Challenge 2026 MC1、MC2 和现有自建运行数据验证跨场景适配能力。

项目的核心不是为每个数据集各做一张静态仪表盘，也不是承诺自动判定责任，而是建立共同的探索流程：**选择数据集 → 建立系统概览 → 发现值得调查的时间段或行为 → 沿参与者、任务和关系追踪事件 → 检查原始证据 → 形成可复核的调查结论。**通用视图负责保持交互一致；数据集配置和场景视图负责呈现各自的语义。

课程/比赛原型以一条完整、可重复讲解的分析路径为交付重点。自动检测、复杂模型训练、云端多租户部署和任意格式数据上传不纳入首版必做范围。对于异常线索，首版以数据已有标签、可解释的规则和分析者筛选为主，并将线索、证据和解释明确区分。

按上述范围，项目难度评估为**中等，约 5/10**：现成数据和 MC1 参考实现可以降低启动成本，三数据集适配、MC2 性能以及跨视图证据链仍是主要工程挑战。若目标扩展为生产级通用分析平台，难度会显著上升，不属于本计划的交付承诺。

**已确定的实施方向（2026-11-04）：**采用 SQLite 作为本地存储与查询方案；重新设计 MC1 前端及共用调查工作区，以清新、聚焦证据的沉浸式交互替代参考工程的多面板堆叠；同时支持浅色、深色和跟随系统。参考工程提供分析思路与实现借鉴，新版从统一数据接口出发实现，MC1 是首个打通的案例（以“外发消息 / 内心审议”双声道对照为核心体验），MC2 与自建集沿用相同交互框架。

## 2. 比赛背景与项目机会

VAST Challenge 2026 的 Design Challenge 关注多智能体系统持续演化带来的行为理解与故障诊断需求。官方背景指出，挑战来自自主系统的行动速度、产生数据的规模、部件之间复杂的交互，以及行为可能偏离人们对“计算机只会按指令行事”的预期。官方鼓励工具结合人工与自动推理，并提出系统映射、预期行为建模、建立基线和概率因果推理等方向。

Design Challenge 是开放式设计题。官方允许假设检测能够及时、可用地提供；不要求必须交付可运行软件，但要求说明尚未实现部分需要什么算法或监控/通信支持。提交形式与其他 Mini-Challenges 类似，包括 HTML 文档、图片和视频，建议长度约 4 页（含图片）。因此，本项目既要形成可演示软件，也要把设计选择、分析过程和原型证据整理成精炼的 HTML 与讲解视频。

三个验证数据集提供互补的问题场景：

| 数据集 | 要解决的问题 | 对原型的验证价值 |
| --- | --- | --- |
| MC1 | TenantThread 并购公告在 2046-06-05 18:00 解禁前约一小时已出现在 FleX。调查两周内沟通、内部 deliberation、决策与发布链，判断是蓄意泄露还是系统在压力下失效，并比较历史行为与先行指标。 | 验证沟通网络、关键事件链、行为/角色偏差和危机时间线。 |
| MC2 | 2046-05-17 04:21，John Windward 向 SaidIT 发出乱码帖子。需要还原发布链、解释内容来源、与历史模式比较，并提出一个有证据支持的干预点。 | 验证系统级活动地图、大规模事件筛选、来源追踪、重复行为与干预分析。 |
| 自建数据集 | 32 次智能体工作流运行，覆盖正常流程、审批绕过、旧版本传播和重复交接。 | 验证 run 级筛选、标签定位、流程回放和已知场景的可解释线索。 |

## 3. 项目目标与成功标准

### 3.1 目标

1. 通过适配层读取 MC1、MC2 和自建数据，不因输入实体格式或事件细节差异而分叉整个应用。
2. 提供一致的时间、实体、关系和事件探索交互，同时保留数据集特有的语义和原始证据。
3. 让用户能够从总体概览深入到一条具体行为链，并沿事件、主体、任务、文档/文件及关系进行交叉筛选。
4. 在 MC1、MC2、自建数据各准备至少一个可复现的讲解案例，支持课堂现场演示。
5. 形成与 VAST Design Challenge 对齐的短篇 HTML 设计说明和演示视频素材。

### 3.2 成功标准

- 数据：三套数据均可加载；总事件数、实体数、时间范围和标签概况与数据目录统计一致。导入或转换时记录错误，不静默丢弃事件。
- 统一交互：时间筛选、事件类型筛选、实体选择、事件详情和“查看原始记录”在三套数据可用；相同筛选条件会联动相关视图。
- 可追溯性：每条可见事件可回到 `event_id`、来源数据集及原始记录；异常线索显示其依据/来源，不把启发式分数表述为事实。
- 场景案例：MC1 可复现泄露前后的沟通链；MC2 可定位指定 SaidIT 帖子的上下文链；自建数据可按运行与标签回放四种场景。
- 性能：MC2 约 18.5 万条事件不会一次性渲染到 DOM 或一次性绘制为图元；常用筛选和选中详情在演示设备上保持可交互。具体响应目标在第一阶段用实际环境基准确定。
- 展示：新环境按 README 步骤能够启动演示；预置案例无需现场手工搜索多个筛选条件即可打开。
- 主题与交互：支持浅色、深色、跟随系统并保存用户偏好；两套主题中图表、提示、证据文本和选中状态均清晰可读。切换主题保持当前调查状态；减少动态效果设置生效。键盘验收范围限定为筛选、时间刷选与回放、事件选择、打开/关闭证据侧栏这几类主要操作，不要求覆盖全部界面元素。
- 提交材料：完成约 4 页含图 HTML 设计说明草稿和一段能讲清问题、交互、发现过程与限制的视频。

## 4. 数据现状与约束

当前数据位于项目根目录的 `data/`。处理后数据使用 JSONL 事件表、JSON 实体表；自建数据另有 `labels.json`。原始 MC1/MC2 压缩包和自建运行级 JSONL 也有保留。

| 数据 | 当前统计 | 需要保留的语义/注意事项 |
| --- | ---: | --- |
| MC1 | 912 条事件，13 个实体，约 1.70 MB 事件文件 | 事件包含 broadcast、one_on_one_chat、side_huddle、action、public_post。时间戳没有时区标记，数据说明明确为源时间、时区未知。回复上下文、收件人和消息内容不能只压成单一 actor-target 边。 |
| MC2 | 185,147 条事件，15,538 个实体，约 167.1 MB 事件文件 | UTC 时间；系统活动类型丰富，包含 email、file、agent task、meeting、SaidIT 等事件。包含 `party_ids` 和带类型的 `relationships`。不少事件没有单一 `target_id`，部分无 `details`；需要用关系列表及原始载荷支持参与者追踪。 |
| 自建数据 | 1,103 条事件、330 个实体、32 次运行 | UTC 时间；标签按 `run_id` 关联，并通过 `affected_event_ids` 定位事件。四种 scenario 各 8 次；21 条记录为 `observed=true`，11 条为 false。旧版本场景中的 false 标签可能表示观察到旧版本读取但没有确认其传播，语义需在界面中准确展示。 |

三类数据共用的事件字段包括 `event_id`、`timestamp`、`actor_id`、`target_id`、`event_type`、`details`、`relationships`、`raw` 等，但实体根结构不完全相同：MC1/MC2 使用带 `entities` 数组的对象，自建实体文件本身是数组。MC1 与 MC2 也不能简单合并时区；MC1 原始时间的时区未知，不能擅自转换成 UTC。

建议数据接入遵循以下约束：

- 规范层统一的是可查询的基础概念，不是把所有事件改写成相同业务含义。
- 永久保留源事件、原始字段、源记录 ID、来源文件/指针及来源时间信息；规范化结果能回溯到原始事件。
- 将时间表示为原始值、解析值、时区/可信度和展示策略；MC1 标注“源时区未知”，MC2/自建数据标注 UTC。
- 多方参与通过有类型的关系边表达，不把 `target_id=null` 误判为没有关系。
- `details` 可含任意结构或缺失，详情面板按类型展示，并提供折叠的原始 JSON。
- 数据版本、转换脚本版本、统计校验结果一并记录，便于演示复现。

## 5. 用户与核心工作流

### 5.1 目标用户

- 课程教师、评审或同学：需要快速理解系统发生了什么，以及可视化支持了什么推理。
- 多智能体系统工程师/分析者：需要定位 actor、工具、任务和系统关系，比较异常行为与正常模式。
- 数据集分析者：需要验证标签、时间范围或原始记录，检查一个告警是否有完整证据链。

### 5.2 核心调查流程

1. **选择案例**：选择 MC1、MC2 或自建集；界面展示数据规模、时间说明、实体类型及可用标签。
2. **建立基线**：浏览随时间的事件量和事件类型分布，查看主要 actor、系统/工具、任务和关系，形成“系统地图”。
3. **发现线索**：使用预置调查入口、数据标签、规则线索或筛选发现异常时段/行为。每条线索显示来源类型（数据标签、规则、分析者选择）及置信/限制说明。
4. **重建链路**：在事件时间线上选中事件，查看前后事件、父子事件、共同参与者、同任务/文档事件及关系边；跨视图选中状态保持同步。
5. **核对证据**：查看消息、details、关联关系和 raw 原始载荷；可追溯回来源文件和官方记录 ID。
6. **记录结论**：以轻量调查笔记记录判断、支持证据、反证、未确定项和建议干预点；导出/截图用于报告和视频。

### 6.1 首版必做功能

| 功能区 | 首版能力 | 主要用途 |
| --- | --- | --- |
| 数据集/案例选择器 | MC1、MC2、自建数据；数据概览；预置案例入口 | 让演示快速进入特定调查，避免不同案例状态混淆。 |
| 全局筛选条 | 时间范围、事件类型、主体、关键词；清空筛选；结果数 | 同一调查状态驱动全部主要视图。 |

| 事件时间线/事件流 | 聚合视图与可选中事件；前后/因果关联标记；事件详情联动 | 回答“发生顺序是什么，关键决策和转折在哪里”。 |

| 调查记录 | 简单笔记、证据引用、当前筛选链接或案例状态导出 | 便于课程汇报和 HTML/视频制作。 |

### 6.2 按数据集配置的分析入口

- **MC1：泄露调查（双声道）。**展示 2046-06-05 18:00 的解禁锚点及此前公开发布；沿对话回复、收件人、channel、内部 deliberation 和行动事件追踪；比较关键角色此前的沟通/发布模式。同一条消息默认提供“外发文本 / 内心审议”对照（对应 `details.content` 与 `raw.internal_state` 中的 reacting、rationalizing、deliberating），用于对照“说出口的”与“正在权衡的”，直接支撑决策点识别与偏离常态的判断；对照展示属于 MC1 专属配置，不进入通用视图。界面应容许多种解释，不预先宣告蓄意或无意。
- **MC2：异常帖子追踪。**以 John Windward 于 2046-05-17 04:21 的 SaidIT 帖子为目标事件，展示精确事件链与系统全景；筛查相关 agent/person、邮件、文件、任务和帖子来源；呈现历史相似模式，并支持选择和论证一个干预位置。
- **自建数据：工作流审计。**按 `run_id` 选择运行，正常与异常情景并排比较；使用 `labels.json` 中的 scenario、anomaly_type、observed、reason 和 affected_event_ids 高亮证据；区分“情景配置为异常”与“本次实际观察到异常”。

### 6.3 设计经验与方案取舍

VAST 2025 Design Challenge 的题目针对知识图谱分析，指出大图规模、属性差异、冲突/不确定和缺失信息会让传统 node-link 图难以阅读；同时强调面向非图专家、支持发现/预测任务，并要求说明交互、适用数据规模、所需预处理和设计局限。对本项目的启发是：关系网络应服务于具体问题，先用时间/角色/类型聚合缩小范围，再显示选中子图；对缺失、推断关系和置信差异给出明确视觉区分；报告中说明规模边界和索引/筛选准备工作。VAST 2025 官方议程还列出 Design Challenge 的“直观查询构建”荣誉提名和“表现力设计”奖项，说明分析入口设计与表达质量同样值得评估。

### 6.4 首版不做/延后

- 端到端无监督/概率因果模型及自动化归责。
- 通用数据上传向导、任意 schema 映射 UI、多租户账户和权限体系。
- 实时在线 agent telemetry、消息总线、告警路由和协同编辑。
- 必须依赖大型语言模型才能工作；如将来加摘要/问答，须返回事件级引用并能被人工核验。
- 生产级云部署和大规模团队运维。首版以本地或单机演示为主。

## 7. 信息架构与视觉呈现

### 7.1 新版调查工作区

重写 MC1 的界面组织和交互状态，建立可复用于 MC2、自建集的工作区。采用大面积阅读空间、低饱和背景、清晰排版与渐进展开；初始只展示当前调查问题需要的视图。保留“概览—筛选—上下文—证据”的分析能力，按需打开基线比较和关系图。

```text
┌ 案例切换 / 当前问题 / 全局筛选 / 主题选择 ┐
├ 案例章节导航 ┬ 调查主画布                ┤
│ 概览         │ 时间泳道 / 聚焦关系图     │
│ 追踪         │                          │
│ 比较         ├ 按需展开的证据侧栏       │
│ 证据记录     │ 消息 / 关联 / 原始记录   │
├ 时间范围刷选 / 当前时间标记 / 回放控制   ┤
└ 当前筛选摘要 / 返回上一步 / 保存证据     ┘
```

左侧的“概览 / 追踪 / 比较 / 证据记录”是讲解顺序与视图状态快照，不是路由页面：切换章节只改变筛选条件、时间窗口和选中对象，主画布始终是同一个工作区，选择与筛选状态不因章节切换而丢失。界面需常驻显示“当前处于章节名 / 自由探索”以及当前筛选摘要，避免用户分不清看到的是预设状态还是自己的探索状态。

时间线、关系图、统计图和证据面板共享选择状态。点击 actor 时，高亮其事件与邻接关系；点击事件时，关系图聚焦对应参与者；从任一视图切换筛选都能看到当前匹配数与筛选条件。关系边显示关系类型与方向，并区分回复、明确收件、共同参与、相似内容与人工假设；时间先后和共同参与本身不能画成已确认的因果关系。

呈现证据时区分四类信息：**原始观测**（数据中实际记录）、**规范化解释**（adapter 推导）、**分析线索**（规则/标签/统计发现）和**人工结论**。颜色不应是唯一编码；缺失值、未知时区和未验证传播须使用文字标签。提供一个预置“演示模式”入口，明确展示正在运行的案例与选中筛选。

### 7.2 沉浸式交互的具体含义

- **双入口：引导调查与自由探索。**预置案例按“背景、线索、追踪、比较、证据”逐步展开；随时进入自由探索，保留当前时间范围和选择。章节用于讲解，不强制用户接受预设结论。
- **聚焦与渐进展开。**选中事件后在侧栏打开证据，原始 JSON 默认折叠；选中主体后展示其相关泳道或局部关系，支持返回全局。侧栏不覆盖正在核查的关键事件。
- **MC1 角色时间泳道。**横轴为源时间，纵向按 agent 分组，消息类型用符号和颜色表达；临近事件可聚合/缩放，详情把公开消息与内部 deliberation 以“双声道”并置展示并标明各自来源；明确记录的回复/收件关系可按需展开。
- **按时间回放。**支持播放、暂停、步进和跳转关键锚点；显示当前时间及累计/窗口模式。回放遮蔽只作用于游标之后的记录：时间泳道、关系图与计数不显示游标之后的事件，游标之前始终全量可查，以保证基线比较和先行指标回溯不被阻断；自由探索可关闭遮蔽，关闭时界面须标明“已关闭回放遮蔽”。
- **调查可回退。**保留筛选面包屑、撤销最近筛选、恢复案例初始状态和固定证据入口；章节切换不清空笔记。
- **克制的动效。**短暂过渡用于解释焦点或时间变化；暂停时布局稳定，减少动态效果时关闭非必要动画。复杂叙事滚动和自动镜头移动放到后续评估。

### 7.3 深浅主题与配色规范

浅色默认用于长时间阅读与课堂投影；提供深色用于专注调查，主题选项为“浅色 / 深色 / 跟随系统”，显式选择保存在本地。以下为初始设计色板，最终经实际图表与投影检查调整。

| 语义 | 浅色 | 深色 | 用途 |
| --- | --- | --- | --- |
| 页面背景 | `#F5F8F7` | `#101917` | 微带青绿的中性背景 |
| 面板 | `#FFFFFF` | `#182522` | 证据与控件承载面 |
| 主文本 | `#172D29` | `#E6F1ED` | 正文、标题、数值 |
| 次文本 | `#50645F` | `#A3B8B0` | 来源、辅助说明 |
| 主强调 | `#0F766E` | `#5EDBC7` | 选择、链接、当前焦点 |
| 异常/风险 | `#B42336` | `#FF8796` | 值得调查的风险，配合标签/符号 |
| 待核验/提醒 | `#8A5500` | `#F4C36A` | 不确定和未确认状态 |

通过语义 CSS 变量统一设置背景、边框、文字和图表颜色；SVG、Canvas、tooltip、空状态与导出图同步适配。事件类别采用固定的独立色表，在两套主题中保持类别含义；主强调色不承担所有类别编码。普通文字对比度以 WCAG AA 4.5:1 为目标，大字及关键图形以 3:1 为目标；键盘焦点明确可见，异常、选中、缺失状态同时使用图形或文字表达。最终验收需覆盖两套主题的实际画面。

图表颜色必须取自同一 token 层：D3/SVG/Canvas 在渲染时读取语义变量，不在组件内写死色值，否则双主题会出现“面板已换、图元未换”的漏改。事件类别色表在两套主题中各维护一份，保持色相与类别语义一致、只调整明度与饱和度；选中态用描边与底色共同表达，强调色不进入类别色表。切换主题后需重绘当前图元，并保持筛选、选中与回放位置不变。

## 8. 技术方案与数据架构

### 8.1 现有基础

工作区目前包含 `data/` 和参考项目 `VAST_Challenge_2026-main/`。参考项目 README 描述了 React + Vite 前端、FastAPI 后端、Neo4j 图数据库和 Docker Compose，原设计聚焦 MC1，具有统一过滤、时间滑块、热力图、事件流、折线图、回复网络及消息上下文面板。其 UI 交互和证据上下文可以作为参考；但其数据导入以旧版 MC1 原始 JSON 为中心，不能直接假定已支持本项目整理后的 MC1/MC2/custom JSONL。

本地参考项目已包含前端依赖与构建产物。新版采用独立的 React + Vite + TypeScript 前端、FastAPI API 和 SQLite 存储，D3 用于需要定制的时间/关系视图。参考工程作为对照材料保留；可借鉴上下文检索、图表算法和数据解释，但新界面、API 与导入逻辑围绕三数据集模型实现。SQLite 方案已确定，首阶段验证重点转为索引、查询性能和新界面原型。

### 8.2 建议架构

```text
MC1 JSONL / MC2 JSONL / custom JSONL + labels
                    │
          数据集 manifest + Adapter
                    │
  canonical event / entity / typed relation / annotation
                    │
   SQLite（事件、实体、参与者、关系、聚合）
                    │
   FastAPI（时间、实体、类型、详情、邻接查询）
                    │
 React + D3 可视分析工作区（共享筛选/选择状态）
                    │
        案例配置 / 调查笔记 / 导出演示材料
```

**规范事件建议字段：**`dataset_id`、`event_id`、`source_record_id`、`timestamp_raw`、`timestamp_normalized`、`timezone_status`、`actor_id`、`participant_ids`、`event_type`、`task_id`、`document_id`、`parent_event_id`、`relationships[]`、`details`、`raw_ref`、`annotations[]`。仅对确实缺少的源信息使用 null；不要为填满字段臆造 target 或 parent。

**实体建议字段：**`dataset_id`、`entity_id`、`entity_type`、`source_value`、`label`、`roles[]`、`attributes`、`raw_ref`。统一将原始实体容器转成内部数组，并保留官方 `org_edges` 或自建实体文件中的关系。

**manifest/适配器元信息：**数据集名称、问题说明、输入文件、时区规则、实体容器路径、participant 提取规则、类型标签字典、可用注释/标签、预置锚点、数据版本与统计校验值。MC1/MC2/custom 分别配置，不在组件中散布 `if dataset === ...` 的字段推测逻辑。

### 8.3 性能和实现取舍

MC2 的事件 JSONL 约 167 MB。导入阶段流式读取并写入 SQLite，生成多级时间聚合；API 分页返回事件，详情及 raw 仅在选中时读取，网络视图限制节点/边并支持按时间、事件类型和选中实体裁剪。对总体趋势优先使用聚合桶，避免浏览器持有重复的大型对象。SQLite 负责查询，D3 负责绘制关系网络，两者没有图数据库依赖。

本地运行只需要前端开发服务和 FastAPI 服务，以及生成的数据库文件；前端构建后可由 FastAPI 托管以简化现场启动。数据导入独立执行并记录源文件校验值和转换版本，查询启动时不重复导入全部数据。Docker 打包可在演示稳定后按需补充。

### 8.4 SQLite 表与查询边界

| 表 | 内容与关键约束 |
| --- | --- |
| `datasets` | manifest、时区策略、统计和导入版本 |
| `events` | 以 `(dataset_id, event_id)` 为联合主键；存储时间、actor、类型、run/task/document、details 与原始记录引用 |
| `entities` | 以 `(dataset_id, entity_id)` 为联合主键；保存类型、名称、角色和来源 |
| `event_participants` | 事件与参与者的多对多关联，标记 actor、recipient、system 等角色 |
| `relations` | 保存事件支持的有向/有类型关系、来源、证据事件及推导方式；组织边可无事件时间 |
| `annotations` / `annotation_events` | 标签/人工记录与事件引用；分开保存 scenario、observed 和 reason |
| `time_buckets` | 按 dataset、时间粒度、类型等预聚合；明确聚合维度，防止多参与者 join 重复计数 |

优先为事件建立 `(dataset_id, time_sort_key, event_id)`、`(dataset_id, actor_id, time_sort_key)`、`(dataset_id, event_type, time_sort_key)`、`(dataset_id, run_id, time_sort_key)` 索引，为参与者/关系建立按实体检索的索引。`time_sort_key` 是查询与分页使用的派生列，由 `timestamp_normalized` 按数据集时区策略生成，与规范字段保持一一对应；MC1 使用源时间朴素排序键，不做任何 UTC 换算，也不生成跨数据集可比的 epoch，仅用于该数据集内部按源时间排序，禁止与 MC2/自建数据混排或比较绝对时刻；锚点时间同样按源时间标注。MC2 与自建数据按 UTC 生成排序键，其 epoch 可用于各自数据集内的时间窗口计算。事件分页以时间与 ID 为稳定游标，带筛选的聚合尽量使用 `EXISTS` 或去重事件集合，统计口径显示为事件数或关系数。

关系检索先提供受限一跳/两跳邻接和按事件引用的链路，再按需求使用递归 CTE 或应用层遍历；必须限制时间范围、深度和结果量。全文搜索可用 FTS5 索引消息/主题/摘要，需检测本机 SQLite 是否支持；若不可用，采用限定范围的关键词查询。大型原始载荷不加入普通列表返回或全部重复索引。SQLite 满足当前单机原型的存储与查询需求，实际响应时间需在 MC2 全量数据上测量。

## 9. 实施阶段与里程碑

以下为小型课程团队的建议节奏，仅作工作量参考，不作为验收条件或排期承诺；实际工期需按团队人数、课时和参考项目可运行程度调整。阶段边界以“上一阶段成果可运行、可演示”判定，而不是按日历判定。若主题与叙事打磨超出预期，优先保证阶段 3 的调查闭环可运行，再看是否补齐视觉细节。

| 阶段 | 建议时长 | 工作内容 | 可审查交付物 / 验收条件 |
| --- | --- | --- | --- |
| 0. 设计与基线确认 | 2–3 天 | 审查参考工程；清点字段；确定 SQLite 表/索引；制作新版 MC1 深浅主题与调查交互草案。 | 三数据集 schema 表、SQLite 小基准、深浅主题设计样例、演示故事板草案。 |
| 1. 数据接入 | 4–6 天 | 定义 manifest 与统一模型；实现三个 adapter；写入 SQLite 并索引事件/实体/关系；读取自建 labels；输出验证报告。 | 三数据集可通过 API 读取；ID、时间、实体数和关系完整性可核验。 |
| 2. MC1 与通用调查工作区 | 5–7 天 | 新建共享前端；以 MC1 打通角色时间泳道、双声道证据侧栏、全局筛选及引导/自由探索状态，随后接入双主题 token 层。 | MC1 可完整调查；切换主题保留状态；共用接口可接入 MC2/custom。若工期紧张，先交付单主题骨架，主题与叙事打磨在阶段 4 之前补齐。 |
| 3. 关系与基线分析 | 5–7 天 | 实现参与者网络、时间/类型聚合、行为对比；给每套数据接入专用案例配置。 | MC1/MC2/custom 各至少有一条从概览到证据的完整 walkthrough。 |
| 4. 演示打磨与评估 | 3–5 天 | 测试 MC2 性能、深浅主题、键盘与减少动效；修复可用性问题；预置案例状态；做 3–5 人快速可用性走查。 | 两种主题在目标设备均可读；可连续演示；关键主张可由事件 ID/原始记录支撑。 |
| 5. 比赛材料 | 2–4 天 | 产出约 4 页 HTML 设计说明、视图截图/草图、视频脚本与录制。 | HTML 讲清问题、设计、证据、局限和下一步；视频不依赖现场临时探索。 |

一个合理的范围控制线是先完成阶段 0–3 的可用闭环，再决定是否增加辅助模型或额外可视化。每个阶段结束都留可运行版本，不将集成风险压到最后一周。

## 10. 评估计划

1. **数据正确性检查：**逐数据集核对事件数、唯一 ID、时间范围、实体引用、关系目标、标签 ID 命中率、缺失字段统计和重复记录。
2. **适配器检查：**每类事件保留输入源指针；MC1 时区不被自动转换；MC2 多方参与边不丢；custom 标签与 `run_id`/`affected_event_ids` 正确关联。
3. **任务走查：**邀请 3–5 位未参与实现的同学，分别执行：定位 MC1 泄露上下文、追踪 MC2 指定帖子来源、比较自建正常/异常运行。记录完成时间、错误选择、证据是否可找回及对线索可信度的理解。
4. **性能检查：**使用 MC2 全量数据测试导入时间、首屏可交互时间、常用筛选响应和关系视图最大图规模；根据测试结果调整聚合粒度和分页。
5. **演示有效性：**按照固定故事板录制，从数据概览到证据链和结论，所有画面均保存事件引用；讲述中明确哪些是数据事实、哪些是推断。
6. **双主题与沉浸交互：**检查浅/深色的正文、图例、悬浮提示、选中和风险标记；验证主题偏好保存与跟随系统；检查回放暂停/步进、筛选回退、键盘导航和减少动效。事件类别色表按实际类别数在两套主题下逐类核对，确认没有仅靠颜色区分且对比度不达标的情况。回放遮蔽边界需专门验证：游标之后不可见、游标之前全量可查、关闭遮蔽有明确提示；“章节 / 自由探索”模式指示与当前筛选摘要常驻可见。课堂投影验证浅色可读性，不能只在开发显示器验收。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 统一模型过度简化事件语义 | 多参与者、内部消息或系统关系丢失，调查结论失真 | 保留 typed relationships、参与者列表、raw payload 和来源指针；由 dataset profile 控制规则。 |
| MC1 时区未知 | 与其他数据或绝对时刻比较时产生错误顺序/偏移 | 按源时间顺序展示，显式标记未知时区，不做 UTC 转换；只在有来源依据时配置锚点。 |
| MC2 数据量导致 UI 卡顿 | 演示失败、关系图不可读 | SQLite/后端筛选、时间聚合、分页和可见节点上限；不全量 DOM 渲染。 |
| 标签被误当成客观真值 | 造成过度确定的异常结论 | 展示标签定义、观察状态和 reason；区分 scenario 与 observed；线索必须能跳到受影响事件。 |
| MC1/MC2 场景差异过大 | 出现过多硬编码和无法解释的“一套视图” | 共享基础交互，按数据集配置入口、类型字典和专用叙事；不强制视图编码同一种业务概念。 |
| 参考工程格式与交互绑定 MC1 | 新版沿用旧假设导致 MC2/custom 难以接入 | 新写统一 SQLite 导入/API 与共享前端；参考工程按分析逻辑/组件算法选择性借鉴。 |
| 沉浸式设计增加操作负担 | 隐藏筛选、过度动画或强制叙事影响分析 | 主问题和筛选摘要常驻；提供自由探索、步进、返回与减少动态效果；用任务走查验证。 |
| 双主题下图表色值散落在组件中 | 深色主题出现不可读图元或漏改，验收阶段才发现 | 颜色统一走 token 层与类别色表，SVG/Canvas 渲染时读取变量；新增视图必须同时在两套主题下检查。 |
| 内心审议被当成已证实意图 | 把模型生成的内部文本当作动机证据，得出过度确定的结论 | 双声道中标注“模型生成的内部文本”及其来源字段；结论需同时引用外发消息与上游事件，不单凭审议文本定性。 |
| 原型做成静态答题展示 | 缺乏系统行为映射与可复用性 | 至少提供一条可探索基线和一条案例链；预置故事用于快速演示，但用户可以继续筛选和追溯。 |
| 计划超出课程周期 | 核心功能未完成 | 锁定首版必做功能；将复杂检测、任意上传、云部署和 LLM 分析放入后续路线。 |

## 附录 A：本计划使用的关键设计原则

1. **共同交互，保留语义。**跨数据集共享筛选、联动与证据查看；各数据集保留其自己的事件词典、角色解释、时区规则和分析入口。
2. **检测线索与结论分离。**自建标签、规则异常和人工判断是不同来源，界面明确标识来源与局限。
3. **从 overview 到 event evidence。**每个聚合趋势和关系结构都能下钻到真实事件；每个结论都有可核查的事件引用。
4. **先做可解释原型。**演示价值来自完整调查过程和设计取舍；复杂算法只有在能够改善或验证核心流程时再进入范围。
5. **为 Design Challenge 留出表达空间。**记录设计演进、取舍和失败想法，说明尚未实现的检测/监控依赖，使软件演示能支撑而非替代设计论证。
