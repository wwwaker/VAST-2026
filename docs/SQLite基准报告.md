# SQLite 基准报告（MC2 全量）

**配套文档：**《多智能体系统异常行为可视分析项目计划书》v1.2 §8.3、§8.4；《数据适配规则》v1.0
**编制日期：** 2026-11-04
**脚本：** `tools/bench_sqlite.py`
**原始结果：** `build/bench_result_mc1.json`、`build/bench_result_mc2.json`、`build/bench_result_custom.json`
**用途：** 阶段 0 交付物。回答三个问题：SQLite 是否够用、索引怎么建、概览聚合要不要预计算。

---

## 1. 结论

SQLite 足够，且余量很大——过滤、详情、实体时间线、全文检索全部在 **10 ms 以内**。

但**概览类聚合不能直接查 `events` 表**。未优化时首屏三个查询合计 327 ms，其中仅小时buckets一项就 270 ms；预聚合后降到 **1.3 ms**。这是唯一一处"偷懒就会在演示时明显卡顿"的地方。

另外三处必须按结论改，否则单项查询会慢 2 个数量级：

| 决策 | 依据 | 收益 |
| --- | --- | --- |
| `participants` 存 `time_sort_key` | 实体时间线要按时间排序，回表排序 6.4 万行 | 64 ms → 1.3 ms（50x） |
| 关系查询禁止查询期 `GROUP BY` | hub 节点有 41,836 条出边，先聚合后 LIMIT | 99 ms → 0.4 ms（248x） |
| 启用 FTS5 | `details_json LIKE '%x%'` 全表扫描 | 107 ms → 0.4 ms（267x） |

## 2. 环境与口径

- Python 3.13、SQLite 3.50（bundled），Windows，D 盘
- FTS5、JSON1 可用；`dbstat` 未编译，体积用"删表 + VACUUM"反推
- 查询耗时取 5 次中位数（聚合类取 3 次），WAL 模式，`synchronous=NORMAL`
- 导入期 `journal_mode=OFF` + `synchronous=OFF`，导入后切回 WAL

**耗时存在环境波动。** 同一份数据多次运行，导入在 **16.4–51.0 s** 之间、Q1 在 **270–673 ms** 之间。原因是本机磁盘与安全软件扫描 223 MB 文件。下表取较优一轮，相对倍率在各轮之间稳定（Q1 为 7.8–12x，Q14 为 85–160x），不影响结论。

## 3. 建库结果

| 数据集 | 事件 | 参与者 | 关系 | 库大小 | 导入耗时 |

MC2 导入分解：事件 14.49 s、索引+FTS 3.81 s、预聚合 1.01 s、实体 0.12 s。

### 3.1 体积构成（MC2，反推实测）

| 组成 | MB | 占比 | 说明 |
| --- | ---: | ---: | --- |
| `participants` + `relations` 及其索引 | 90 | 40% | 494k 行，`entity_id` 是 35–40 字节字符串且每行重复 |
| `events` 主表 | 52.6 | 24% | 其中 `details_json` 16.7 MB |
| `event_raw` | 53 | 24% | 原始载荷 39.5 MB + 主键索引 |
| `events` 三个索引 | 22.6 | 10% | 每个约 7.5 MB |
| FTS 索引 | 4.3 | 2% | 文本 1.3 MB，索引开销很低 |
| 其余（entities / time_buckets / stat_counts） | ~2 | 1% | — |

两点判断：

1. **FTS5 几乎免费**（4.3 MB / 2%），没有理由不建。
2. **体积由字符串主键主导**，不是由原始数据量主导。若将来需要压缩，正确做法是给实体分配整数代理键，可省约 90 MB 中的大部分；但 223 MB 对本地原型不构成约束，**不建议首版做这个优化**。

### 4.2 优化后

| 优化项 | 前 | 后 | 倍率 |
| --- | ---: | ---: | ---: |
| O1 小时聚合（读 `time_buckets`） | 270.12 | 25.47 | 10.6x |
| O2 天级聚合（读 `time_buckets`） | 247.05 | 1.22 | 202x |
| O3 类型分布（读 `stat_counts`） | 51.10 | 0.23 | 222x |
| O4 Top 主体（读 `stat_counts`） | 50.99 | 0.45 | 113x |
| O9 实体事件（去规格化时间键） | 64.31 | 1.28 | 50x |
| O14 一跳关系（LIMIT + 应用层聚合） | 99.19 | 0.40 | 248x |
| 首屏三查合计 | 327.44 | **1.34** | 244x |

预聚合的导入期成本：`time_buckets` 1.01 s、`stat_counts` 0.17 s。相对 14.49 s 的事件导入，可以忽略。

### 4.3 O1 仍为 25 ms 的原因

返回 **11,577 行非空组合**（24 种事件类型 × 1,653 个小时桶，11,577 是其中实际有数据的格子）。耗时主要在行物化，不在聚合。

**因此不建议把小时 × 全类型的时间序列直接交给图表。** 建议：

- 默认用天级粒度（70 点，1.2 ms）；
- 需要小时粒度时，只取选中类型（最多 5–6 条序列）；
- 其余类型合并为"其他"，或按需展开。

### 4.4 Q14 慢的根因

`GROUP BY` 在 LIMIT 之前执行。Top 主体 `zoey_drydock` 有 41,836 条出边，即使只要 300 条也要先聚合 4 万行。去掉 `GROUP BY`、各分支先 `LIMIT` 再合并，降到 0.4 ms。需要真实边权重时，在导入期建 `relation_degree` 汇总表，不要查询期计算。

## 5. API 耗时预算

按实测给出各端点的目标值，作为阶段 1 的验收线：

| 端点 | 查询组合 | 目标 |
| --- | --- | ---: |
| `GET /api/datasets/{id}/overview` | `stat_counts` + `time_buckets(day)` | < 5 ms |
| `GET /api/events` | 时间 + 类型 + 主体筛选，分页 100 | < 15 ms |
| `GET /api/events/{event_id}` | 详情 + raw + 参与者 | < 5 ms |
| `GET /api/entities/{id}/events` | 去规格化时间线，上限 300 | < 10 ms |
| `GET /api/entities/{id}/neighbors` | 双向各 150 条 | < 10 ms |
| `GET /api/search` | FTS5，上限 200 | < 10 ms |
| `GET /api/timeline` | `time_buckets(hour)`，类型数上限 6 | < 30 ms |

上表均为数据库耗时；加上 FastAPI 序列化与网络，留 2–3 倍余量仍在可交互区间。

## 6. 落地要求

1. **导入期必须生成** `time_buckets`（hour、day 两级）与 `stat_counts`（type、actor 两类），运行期只读。
2. `participants` 冗余 `time_sort_key`，索引为 `(dataset_id, entity_id, time_sort_key)`。
3. `relations` 允许 `src_id` 为空。实测 38 条关系边的源事件 `actor_id` 本身就是 null，derivation 记为 `source:relationships:actor_null`。**不要为了凑出源节点而臆造 actor。**
4. 关系邻接不得在查询期做 `GROUP BY`；一律先限流再在应用层聚合。
5. 关键词搜索走 FTS5；`LIKE` 只允许用于已限定 `actor_id` 或时间窗的小范围查询。
6. `raw` 独立成表，仅详情读取。实测单条读取 0.03 ms，分离没有代价。
7. 事件列表分页大小 100 已被验证足够快；不需要服务端游标之外的优化。

---

## 7. 遗留风险

1. **导入耗时波动 3 倍**（16–51 s）。演示环境首次启动需要现场导入时，应预生成数据库文件随项目分发，而不是让用户等待。
2. **未验证并发**。基准为单进程单连接。FastAPI 若使用多 worker，WAL 可支持多读一写，但需要实测连接池配置。
3. **未验证两跳邻接**。当前只测了一跳；两跳需递归 CTE，规模会显著上升，阶段 3 必须单独设限。
4. **未验证浏览器侧渲染**。数据库 1.3 ms 不代表图表能画 11,577 个点。性能上限可能在前端，需要在阶段 2 实测。
