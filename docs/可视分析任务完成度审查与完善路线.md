## 1. 结论与审查范围

当前项目已完成统一数据接入、查询和日志浏览的主要基础设施，但尚未完成项目计划书承诺的可视分析任务闭环。适合称为“可运行的调查工作区原型”，暂不宜称为“三套场景分析已完成”。

缺口不应按页面数量衡量，而应检查：用户能否发现问题、重建关键链路、选择合理对照、核对原始证据、记录并复现结论。三个主视图可以作为稳定导航，但画布内需要增加与数据集任务相符的表达与交互。

本次审查读取了项目计划书、主工程前后端、SQLite 实库、处理后事件、自建标签、final-data 派生分析和参考工程说明；直接读取了官方 MC1/MC2 ZIP 内的 Answer Sheet，未依赖联网二手答案。主工程是根目录的 backend/frontend；VAST_Challenge_2026-main 是被 Git 忽略的独立参考工程，其功能和提交材料不能计入主工程完成度。

核验结果：三套数据的数据库事件数为 912、185,147、1,103；实体数为 13、15,538、330。运行 npm run build 通过 TypeScript 检查与 Vite 构建。检查了现有截图，但本次未重新执行浏览器交互验收或可用性实验；构建通过不代表分析任务通过。

## 3. 优先修复的准确性问题

### 3.1 关系图和比较没有遵循完整调查上下文

- RelationGraph 只读取 dataset、focusedEntityId，fetchGraph 只发送 dataset/center/depth；后端 graph 也不接收时间、类型、关键词或回放游标。因此刷选某天后看到的图仍是全时段关系。
- EventStream 发送时间、类别对应类型、actor、关键词，但不读取回放 cursor/masking。用户回放到某个时刻时，列表仍可能显示未来记录。
- CompareView 只使用时间范围和维度，未使用 actor、类别、关键词和回放边界。
- OverviewView 取全局概览，忽略主体和关键词。全局概览可以保留为上下文，但必须标明“全局”，并叠加当前筛选结果，不能让用户以为所有视图都是同一切片。

建议定义统一 FilterContext，并让所有查询明确返回 applied_filters、matched_events、scope。图中的无时间组织关系应作为独立背景层保留并标注。历史基线可以使用不同窗口，但其样本条件和时间边界必须显式可见。

### 3.2 图的证据次数重复累计

graph.py 中，同一条聚合边可分别由出边、入边或不同种子节点扩展命中，随后再次累加已计算的 COUNT(*)。

本次直接调用图查询：MC1、中心 MC1:agent:legal_agent、depth=2、node_limit=80。legal_agent → comms_huddle、broadcast_to、adapter:recipients 这条边返回 evidence_count=252；同条件查询 relations 表的实际行数为 126。

建议按稳定边键只接受一次聚合结果；如果跨来源合并，按事件 ID 去重。边还需支持打开完整证据列表，不能只展示次数或一个 MIN(event_id)。

### 3.3 概览把关键低频类型错误编码为“其他”

OverviewView 请求 topTypes=6；后端先保留频率最高的六种事件，把其余类型汇总为 __other__；前端再将这些类型映射成八类。

MC2 前六类实际是 check_email、assign_agent_task、read_file、queue_subordinate_task、create_file、delete_file。post_saidit 等发布类型全部失去原类别信息，导致“公开发布”这类核心调查行为在概览中被归入“其他”。这不是没有发生发布，而是聚合顺序隐藏了发布。

建议先按完整类型字典映射语义类别，再聚合类别；如果只显示 Top N，需将原始类别与类型明细一起返回。CUSTOM 的 file_read、file_write 也未纳入前端文件操作字典。

### 3.4 正常运行被描述为异常情景

EvidenceDrawer 对全部 observed=false 的标签统一显示“已配置为异常但未观测到”。实库中 normal 场景的 8 次运行也是 observed=false，且有 40 个关联事件，当前分支会误标这些正常证据。

至少分为：normal 正常对照；异常 scenario 且 observed=true 已观测；异常 scenario 且 observed=false 未观测到目标结果。stale_version 中还要分开“读到旧版”“尝试发布旧版”“确实发布旧版”“被拒绝”，不能仅凭一个 observed 字段解释所有阶段。

### 3.5 时间编码和比较边界需要校正

- 概览横轴按已出现桶的数组索引等距绘制，缺失桶被省略。MC1 跨 20 个日历日只有 14 个日桶、23 个小时桶，小时之间的长间隔被压缩。建议使用真实时间比例或补齐零桶；若使用轮次轴，应明确标为“轮次”。
- 回放只按 bucket_start > cursor 隐藏整桶，当前桶中晚于游标的事件仍计入整桶，存在未来信息泄漏。需要重新查询当前部分桶，或显式采用“截至已完成桶”的近似模式。
- 比较端点用闭区间，自动历史窗结束于 start、当前窗开始于 start，边界事件会进入两个样本。改用统一的半开区间 [start,end)。
- 只提示“基线完全在数据之前且为零”不足以处理部分覆盖；应显示有效观察时长、样本量、数据覆盖率。数据缺失不能自动当作零活动。
- 换数据集未清空 focusedEntityId，可能把旧数据集实体带进新图；调查状态需要按数据集隔离。

### 3.6 预置解释应作为待核验假设

manifest.py 直接把 SwiftWren_further_instructions.md 的任务接力写成“唯一入口”，当前画布没有展示证明这句话所需的完整链路与历史对照。

“最多选一个干预位置”是提交约束，不表示数据已经证明只有一个入口。先把该建议标记为候选假设，随后用目标链中的事件、两次历史实例、适用范围及潜在正常任务影响论证。移除观测图中的边只能说明该观测路径被切断，不能证明真实系统改变后的结果。

### 3.7 自建事件的精细顺序在入库时被损失

loader.parse_epoch 返回整数秒，events.time_sort_key 因而丢弃了源时间的小数部分。CUSTOM 的 1,103 个源时间戳彼此不同，但按“run_id + 秒”分组后，有 184 组同一运行内的事件共享一个秒。当前列表用“秒 + UUID”排序，这会把同秒内的审核、读取、尝试发布与结果按 UUID 重排，无法正确支持毫秒级流程审计。

修复时不能仅改变画布格式化：导入、索引、分页游标、parent 边的时间核验、比较窗口和回放都需要使用同一高精度键。第 6 节给出整数微秒方案，并保留 MC1 的未知时区标记。

### 3.8 导入校验失败不能保证旧库不受影响

cli.main 在 load_dataset 后先 conn.commit，再根据 stats.checks 累积 all_ok，最后才以非零码退出；--fresh 还会在导入开始前删除目标旧库。README 中“不写入半成品数据”的表述目前没有得到这段实现保障。

后续变更表结构时，采用同目录临时库完整构建、校验后替换的流程；失败保留旧库。数据库版本升级和派生统计导入应共享这套流程，见第 7 节。

### 3.9 文件“操作轨迹”不包含文件“内容”

再次检查 MC2 中 191 条 details 含 SwiftWren 的记录：出现的字段只有 target_agent、task、args、action、target、size_hint、forum、content_source。已核查的 MC2:event:21202 创建记录只给出 SwiftWren.txt 和 size_hint=30615；MC2:event:373902 帖子只给出 content_source=SwiftWren.txt。不能由这些字段复原正文，更不能根据文件名宣称解码了帖子的含义。

因此 MC2 Q2 必须拆成两个验收项：“内容来源文件可追踪”和“内容含义有直接证据”。前者可实施；后者先审计官方包和所有相关载荷是否提供正文。未提供时，交付可复核的缺失报告及有界结论，不用推测文本填补。第 11 节规定该审计的实现及页面状态。

### 5.3 CUSTOM：运行级流程对照与审计

1. 运行总览：32 行 run 矩阵，显示模型、任务、scenario、observed、发布状态、版本结果、交接次数和耗时；条件可筛选。
2. 单次流程泳道：按数据中的 controller/coordinator/researcher/writer/reviewer/publisher 六种角色分道，用相对运行时间表达消息、交接、审核、读取和发布；parent_event_id 和明确流程关系连接事件。
3. 配对比较：默认选择 matched_comparisons 中同模型、同任务的正常对照，按流程阶段对齐，同时保留真实耗时；突出缺失审核、额外交接、版本差异。
4. 审核与版本面板：同时展示 selected/expected/read/published version、review hash、publish hash、审核有效性和拒绝原因。

已知批次结果可直接组织为可核验案例：8 次正常；8 次审批绕过均 observed=true；8 次重复交接均 observed=true；旧版本条件 8 次中 5 次实际发布旧版、3 次未观测到目标异常。后者仍需展示旧版读取与发布被拒绝等阶段，不能简单涂成“无异常”。

后端必须显式保留 run_id；当前 events 表仅存 task_id，自建源数据中的 task_id 是 run_id + ':task'，不应长期以字符串推断替代正式运行维度。labels 表的 run_id 及 affected_event_ids 只适合定位标签证据，不能替代全部运行事件的查询。

验收：选择任一运行可查看完整流程；选择正常对照可自动成对显示；从版本/审核差异能定位到事件，不仅是阅读标签给出的结论。

## 6. 先固定公共数据契约，避免各视图独立解释筛选

### 6.1 时间：整数微秒、半开窗口、数据集内排序

新增 events.time_sort_us，SQLite INTEGER，值为当前排序时间的整数微秒。UTC 数据以 UTC 计算；MC1 仅把源时间字面量映射到一条本数据集内部的坐标轴，timezone_status 仍为 unknown，禁止与 UTC 数据混排。所有公开响应同时保留 timestamp_raw、timezone_status，不能把 MC1 显示成 UTC。

Python 不使用 int(datetime.timestamp() * 1e6) 生成微秒键，而用规范化 datetime 与参考点之差的 days、seconds、microseconds 进行整数运算，避免浮点舍入。CUSTOM 当前最多六位小数可完整保存；未来更高精度输入先报错，不静默截断。

统一窗口为 [start_us,end_us)，SQL 使用 >= 和 <。回放 cursor_us 的界面语义为“显示时间不晚于此游标的事件”，因此有效截止为 min(end_us,cursor_us+1)。若 start_us 不小于有效截止，返回空集，不偷偷交换端点。游标恰好落在一条事件时，该事件可见。当前 2046 年的微秒值小于 JavaScript 安全整数上限，前端仍可使用 number；序列化前做 Number.isSafeInteger 检查。

新增索引：

```sql
CREATE INDEX idx_events_time_us ON events(dataset_id,time_sort_us,event_id);
CREATE INDEX idx_events_actor_us ON events(dataset_id,actor_id,time_sort_us,event_id);
CREATE INDEX idx_events_type_us ON events(dataset_id,event_type,time_sort_us,event_id);
CREATE INDEX idx_events_run_us ON events(dataset_id,run_id,time_sort_us,event_id);
CREATE INDEX idx_part_event_entity ON participants(dataset_id,event_id,entity_id);
```

events 同时新增 run_id、target_id、version、channel_id、source_file、source_ordinal。前三项支持自建审计，channel_id 支持 MC1 渠道比较，source_file 配合现有 source_json_pointer 溯源，source_ordinal 记录 JSONL 行序。缺失字段保留 null。同微秒时 event_id 仅作为稳定分页次序，不宣称能解析真实先后；source_ordinal 可展示源记录顺序，也不能作为因果证据。旧 time_sort_key 暂保留兼容旧聚合，所有新查询走 time_sort_us，迁移完成后再清理旧索引。

事件分页改为版本化游标：base64url 编码 `{v:2,t_us,event_id,direction,filter_hash}`。filter_hash 由排序后的有效筛选生成；更换筛选后重置游标，收到不匹配游标返回 400/cursor_filter_mismatch。全量检索不能以第一页的 LIMIT 结果代替匹配集合。

### 6.2 筛选上下文：明确 actor、参与者与图焦点的区别

新增 backend/app/query/filters.py 与 frontend/src/data/filterContext.ts。Python 用 Pydantic 模型验证参数，再生成固定列名的参数化 SQL；前端只负责序列化，不自行实现另一套筛选逻辑。

```ts
interface FilterContext {
  dataset: "MC1" | "MC2" | "CUSTOM";
  startUs: number | null;
  endUs: number | null;
  categories: number[];
  eventTypes: string[];
  actorId: string | null;
  participantId: string | null;
  runId: string | null;
  keyword: string;
  cursorUs: number | null;
  masking: boolean;
}
```

固定规则：

1. actorId 表示执行者相等；participantId 表示事件任一参与者命中，用 EXISTS participants 查询，避免多角色 join 导致重复计数。
2. 图中的 focusedEntityId 只是探索中心，点击节点只改变图焦点；用户点击“筛选该参与者”才设置 participantId。界面同时显示这两个状态。
3. categories 与 eventTypes 同时指定时取交集。未传表示不限；一个非空类别经字典解析后没有任何匹配类型时必须返回零条，不能因 types=[] 被当成“不限”。
4. runId 仅 CUSTOM 有效；MC1/MC2 收到非空 runId 返回 400/unsupported_filter。未知数据集 404，非法窗口 400。
5. keyword 默认是普通文本检索，FTS 中的引号与标点由服务端转义；如果提供高级检索模式再显式允许 FTS 语法。文件名解析走实体字段，不借助未经转义的 FTS 表达式。
6. 时间范围用于当前观察窗口，cursor 只在 masking=true 时限制数据；masking=false 不限制记录，并在画布上显示关闭状态。
7. 切数据集统一清空 filters、focusedEntityId、selectedEventId、runPair、cursor、播放状态及未固定的 trace。仅主题和布局偏好保留。

所有列表、聚合和图响应增加共同 meta：

```json
{
  "meta": {
    "contract_version": 2,
    "dataset_id": "MC2",
    "data_version": "sha256-of-source-events",
    "scope": "filtered",
    "applied_filters": {},
    "effective_time": {"start_us": null, "end_us": null},
    "matched_events": 0,
    "truncated": false,
    "next_cursor": null
  }
}
```

示例中的空值只是格式示意。matched_events 指去重事件数，不是边数、图节点数或已加载行数。scope=global_context 的背景概览只忽略用户选择的局部时间窗和非时间筛选，仍然服从 cursor/masking 截止；必须与 filtered 系列分开返回、分开标注，不能在回放中泄漏未来桶。数据集原始总规模可作为静态元信息显示，但不能标为当前已观测事件数。静态组织边使用 scope=static，不参与 matched_events。

### 6.3 类型字典：服务端决定语义，前端决定颜色

新增 backend/app/domain/event_types.py，按 dataset+event_type 保存 category、is_action、is_receipt、display_label。GET /api/datasets/{dataset}/capabilities 返回完整类型字典及该数据集支持的筛选/视图；frontend/theme/categories.ts 保留八类颜色和样式，不再维护独立 TYPE_MAP。

### 6.5 查询和证据边的数据结构示例

统一筛选器产生 EventSelection，其中含 where_sql、params、effective_range、filter_hash。列表、COUNT、聚合和关系查询全部使用这一个选择器，不在每个 router 再写一套条件。以“数据集+窗口+参与者”生成的 SQL 结构为例，省略未启用的可选条件，不能把空列表直接拼成 IN ()：

```sql
SELECT e.event_id,e.time_sort_us,e.actor_id,e.event_type
FROM events e
WHERE e.dataset_id=:dataset
  AND e.time_sort_us>=:start_us
  AND e.time_sort_us<:effective_end_us
  AND EXISTS (
    SELECT 1 FROM participants p
    WHERE p.dataset_id=e.dataset_id
      AND p.event_id=e.event_id
      AND p.entity_id=:participant
  )
ORDER BY e.time_sort_us,e.event_id
LIMIT :page_size_plus_one;
```

关系边聚合将同一 WHERE 应用到与 events 联结的 relations，再 GROUP BY src/dst/relation/derivation，COUNT(DISTINCT r.event_id)。静态组织边另外查询。证据分页使用完全相同的关系键与事件筛选，GROUP BY e.event_id 后按精确时间排序。FTS 命中用完整命中集合与 dataset 约束；性能实现沿用现有先命中 rowid 再回表的思路，并测试查询计划，不为了提速提前只取前 50 个命中来计算全局统计。

trace 边使用固定结构，避免“实线/虚线”只有视觉上有区别：

```ts
interface TraceLink {
  id: string;
  sourceId: string;
  targetId: string;
  relation: string;
  provenanceKind: "recorded" | "derived" | "candidate" | "analyst";
  temporalStatus: "valid" | "same_time" | "future_reference" | "unknown";
  evidenceEventIds: string[];
  sourcePointers: string[];
  ruleId: string | null;
  explanation: string;
}
```

节点另有 kind=event/entity/context；只有 event 节点计入日志事件数。derived 表示确定的字段映射，不等于高置信因果；candidate 必须携带规则和解释；analyst 保留人工作者/版本。前端与导出使用同一 provenanceKind，而不是各自凭关系名猜样式。

## 7. 数据库升级与派生数据接入：可执行的导入方案

### 7.1 原库和人工笔记的处理

应用主库可从事件文件重建，优先采取 schema v2 完整重建，不尝试从 task_id 猜 run_id 或从整数秒恢复微秒。build/notes.db 保持独立，新增人工表通过独立幂等迁移创建，不参与 --fresh。

修改文件：backend/app/ingest/schema.py、loader.py、cli.py、config.py；新增 ingest/artifacts.py、ingest/validate.py。loader 中 INSERT INTO events VALUES 的位置参数写法改为显式列名，避免加列后写错字段。使用 PRAGMA user_version=2 和 datasets.import_version 表明版本；服务启动遇到旧版主库时返回明确的 schema_outdated，给出重建命令，不继续执行 v2 查询。

完整导入流程：

1. 在目标主库同目录创建 mas.next.<随机标识>.db。导入规范事件、实体、标签，再导入核验通过的派生文件。
2. 在临时库执行索引、FTS rebuild、统计；检查事件/实体基线、事件唯一性、源哈希、标签引用、run 汇总和派生引用覆盖率。
3. 必需检查有失败即退出非零，写 build/ingest-validation.json；旧 mas.db 保持不变。可选派生文件缺失只将相应 capability 设为不可用，不影响通用日志浏览。
4. 通过后关闭临时库并做 quick_check。停止正在占用主库的后端，在 Windows 上确认连接释放，再备份旧库并替换；WAL 使用 checkpoint，不能把主文件与旧 wal/shm 混用。替换失败保留旧库与临时库，输出准确错误。
5. 重新启动服务；GET /api/health 增加 schema_version、data_version、artifact_status。--dataset 路径也必须在临时副本上处理并验收后替换，不能退回逐数据集提前提交。

重建只操作项目 build 目录中的已解析路径，旧库备份保留到新库验收完成。不要在迁移过程中自动删除人工 notes.db。

### 7.2 派生文件定位、哈希与 ID 映射

配置增加 MAS_ARTIFACT_ROOT，默认 ROOT/final-data。读取 process/views/manifest.json，其中所有 path 相对于 final-data 根目录，不能再相对于 process/views。逐项检查路径仍在根目录内，校验 manifest.files 中的文件 SHA-256；再把 datasets.*.source_sha256 与当前 data/processed 对应事件文件的哈希比较。

本次三套源事件文件均核对一致；这只证明当前版本可接，不替代导入时检查。哈希不一致时关闭该派生能力并报 artifact_stale；若用户显式要求必需派生数据，则阻止生成新主库。source_entities 和 labels 也计算哈希并记录，避免“事件未变、实体或标签已变”时继续沿用旧结论。

MC1 派生 message_ids 使用官方 source_record_id，入库前用 (dataset_id,source_record_id) 精确映射到 events.event_id。agent_id 也使用 entities.source_value/规范化别名建立映射并校验，不能机械拼接 agent_id，因为源项目和当前角色命名存在别名。MC2、CUSTOM 的 event_ids 已是规范 ID，仍需逐条验证引用。

### P0-04 修复标签与时间图表达

**标签：** normal → “正常对照”；非 normal 且 observed=true → “已观测目标异常”；非 normal 且 observed=false → “未观测到目标异常”；未知标签 → “未标注”。正常事件不能出现风险色异常文案。运行阶段结果另用版本/审核审计展示，不复用 observed 为所有阶段定性。

### C-01 建立运行索引和可核验的审计结果

**新增：** backend/app/domain/custom_audit.py、routers/runs.py；复用 artifacts.py、events 表和 labels。

**输入：** 规范事件按 run_id 分组；views.runs 的 model/fixture/阶段/指标；labels 的 scenario/observed；matched_comparisons。model 可由 run_started.details.model 交叉核查，fixture 由 researcher 读取的 fixture 路径核查，不从 run_id 推断模型或任务。

**处理顺序：**

1. 为每个 run 计算 min/max time_sort_us、event_count、事件类型分布、发布尝试/结果 ID。检查恰有一个 run_started；缺少 run_finished 的运行标 incomplete，不按失败或成功猜测。
2. 将源标签和重算审计分开存：source_annotation 保存原 observed/reason，audit_results 保存以下规则、判定、证据 ID 和 algorithm_version。
3. 校验 views 中已计算指标与源事件重算一致。存在差异时输出具体 run/字段/双方数值；不能为了匹配标签而修改计算。
4. 关联正常对照：优先采用已核验的 matched_comparisons。没有匹配时显示“无匹配正常运行”；同模型/fixture 多个正常候选时列出候选供选择，不自动挑最快的一次。

**审计规则，按每次 publish_attempt 而非整个 run 只算一次：**

| 规则 ID | 数据与计算 | 输出状态与证据 |
| --- | --- | --- |
| REVIEW-01 | 用 attempt.details.review_event_id 查 review_decision；要求同 run/document、approved=true、review 时间不晚于 attempt、非空 review.sha256 与 attempt.sha256 一致、已知 version 一致 | valid / invalid / unknown，返回 review 和 attempt ID；不存在引用或相悖字段为 invalid，必要字段未记录为 unknown |
| VERSION-01 | attempt.version 对 attempt.details.expected_version；publisher read 使用明确 read_event_id 回查，核对同 run、actor、文档、版本和哈希 | current / stale / unknown；额外返回 read/version/expected 的证据 |
| PUBLISH-01 | result.details.attempt_event_id 关联 attempt；成功结果才比较 result.version/hash 与 attempt/read | published_current / published_stale / denied / failed / unknown，返回 attempt/result/read ID |
| REVIEW-02 | success 结果关联的 attempt 在 REVIEW-01 中为 invalid | published_without_valid_review=true；unknown 不强行计为 true 或 false |
| HANDOFF-01 | 按 task_id 统计 task_handoff 的 source_role→target_role；每对 max(0,count-1) 求和，另列 A→B→A 回返序列 | repeated_pair_count、循环路径候选与 handoff ID；仅称“重复交接线索”，不自动断定无意义循环 |

review 已批准但 version/hash 不同属于无效凭证；details.valid_review 只作为 reported 值，与 recomputed 并列。不能因为前端看到了 approved=true 就认定本次发布受有效审核。run 级结果由各 attempt/result 汇总，保留多次尝试，即使当前批次每 run 只有一次，也不把实现写死成固定数组位置。

**接口示意：** GET /api/runs/{run_id}?dataset=CUSTOM 返回 run、events、recorded_links、call_intervals、audit。audit 每项有 rule_id/status/reason/evidence_event_ids；缺失 evidence_event_id 不能被界面生成的编号替代。

**验收：** 总计 32 run、每种 scenario 8 run；所有事件完整归属某一运行，汇总等于 1,103；24 对对照合法；审计结果与已核验派生结果逐项比对并输出差异报告。模型/fixture 元信息缺失时也要能浏览事件，只是不能伪造匹配。

### M2-02 文件轨迹和事件链算法

**数据建模：** file_operations 从 relations 中的 file_path、queued_file_path、post_content_source 等文件关系生成，并关联 events。按 (file_id,event_id,relation) 去重；file_tracks 仅用于核对轨迹覆盖，不用它替代原始关系。文件搜索优先实体完整 source_value，其次候选路径；大小写与路径规范必须记录，不仅按 basename 匹配。

**trace 分成两层：**

- 记录层：post→content_source 文件、event→typed participant/file、明确 parent/reply 等直接可查引用。事件节点与文件实体节点分别编码，不把一个文件节点画成“发生了一次操作”。
- 候选层：同文件上的时间顺序、同目标 agent 的接力、接力后读取等推测关联；每条返回 rule_id、支持事件、时间间隔和 confidence_kind=candidate。默认可见但虚线，不参与“已证实路径”的统计。

**可执行追踪过程：**

1. 从 root_event 查直接文件/参与者关系，以精确 file_id 取出窗口内文件操作，按 time_sort_us 排序。
2. 查目标发布者涉及的接力记录；只有记录明确给出 task/read_file/path 或 queued_file_path 时，才能把对应指令文件关联进来。SwiftWren.txt 与 SwiftWren_further_instructions.md 的共同前缀只可作为搜索提示，不能单独建立传播边。
3. 一条 queue 记录提供 sender、target_agent、task、args.path。对于“它是否导致后续读取”，先查显式引用；没有引用时只生成同 target_agent、同 file_id、时间不早于 queue 的候选。并列候选全部保留限定样本，不武断选择最近一条。
4. 使用 visited 节点/边键避免循环；事件预算默认 100、最大 500，实体预算另限 100；按显式引用优先、离种子更近优先展开。返回预算、截断原因和可继续展开的 frontier。
5. 回放时种子晚于游标则请求提示不可用；显示历史基线时不能通过 trace 侧路读到未来事件。窗口之外的关联返回“存在但未加载”的计数和主动扩展入口。

进入链路时继承当前筛选。如果 actor/关键词过滤排除了上游，不悄悄忽略这些条件：画布显示“当前仅含匹配节点”，提供“展开完整调查上下文”。用户点击后保存原筛选快照，清除 actor/keyword 等局部约束并扩大时间窗，继续保留 dataset 和回放截止；状态栏显示变更且支持返回。证据侧栏的“查看文件轨迹”同样使用这一规则，避免列表已筛某 actor、链路却暗中出现另一批记录而不说明。

**前端：** 新增 views/mc2/SourceTrace.tsx、FileTrack.tsx。横轴是实际时间；泳道是 actor 或系统，文件作为附着节点。跨 8 天的长间隔可以折叠空白，但必须画断轴并注明折叠天数，提供真实时间模式。点击事件打开现有详情；点击文件打开操作轨迹；点击候选边显示为何关联及缺少的确定性字段。

**验收：** 目标包每个节点都能回到事件或实体；21202/21209/373902 可定位；SwiftWren 相关 191 条 details 命中只能作为交叉检查，不作为算法必须凑出的链长。文件名相似而无支持关系的测试样例不能被画成明确传播。

### M2-05 单点干预的可核验论证

首版将干预配置存为一个 candidate，字段为 location、predicate、target_chain_ids、evidence_ids、limitations。候选位置可从 queue_subordinate_task 的任务文件转交校验开始，但不再在 manifest 声称“唯一入口”。

矩阵 7 行 agent，列可选 day/hour/round。计数默认按记录消息数，渠道筛选和 keyword 使用统一上下文。无记录的格显示中性空状态，非“未执行职责”。点击格设置时间+actor，Shift 点击扩大范围；渠道切换作用于泳道和事件流。

决策泳道最少包含：外部环境轨、禁发约束轨、agent 消息轨、公开发布轨。环境 context 与消息严格分层；source precision=round 的记录用轮次区间/不确定位置，不能凭轮次起点伪装精确发生时刻。人工 event_markers 显示 analyst 来源，event_links 的 possible_enabling_context、same_round 不改名成 confirmed_cause。

首条内部确认 MC1:event:20460605_21_026、第三方报道 context、18:00 解禁并置。17:00 外部报道没有对应内部发帖事件时使用 context_id，不能制造一个 event_id。当前未加载或缺失的环境内容显示缺口。

双声道复用现有组件；在泳道筛选中提供“含审议记录”，但标题同时显示当前覆盖数和全库 86/912。用户可把消息和审议片段固定到同一 finding，UI 保留二者不同的 provenance。

验收：用户能找到约束、发布节点和引用关系，逐步核查上游；同轮共现和人工判断不会被绘为已证实因果；环境与消息计数不会相加冒充 912 条事件的增长。

### M1-03 典型行为画像与历史线索

新增 domain/mc1_rules.py、views/mc1/BehaviorProfile.tsx、LeadingIndicators.tsx。首版不用情绪分数判断角色偏离；优先使用可解释、可数的指标：

- 每个 actor 的内部/公开渠道分布与消息频率；对照相同 actor 的既往窗口。
- 沟通对象分布：recipient、mention、valid_reply 分层计算；广播不摊成任意两人私聊。
- 有效回复延迟：只用 reply_valid 且时间可比的记录，显示 n/median/p90；future reference 计入数据质量，不计负延迟。
- 公开发布中并购名称/代号的命中：固定词表+命中片段+文本来源字段；先当内容检索线索，不直接断言违规。
- 需要审核的行为：只有已记录制度/指令能给出角色或渠道约束时，建立“预期规则”并引用源记录；没有明确审核要求时不把“未找到审核消息”判为绕过。

每条规则配置至少含 rule_id、version、适用角色/渠道、关键词或字段条件、expected_behavior_source_ids、limitations。对关键词命中只给 hit=true 与引文，不给故作精确的置信分。用户可以标记支持、反对、待核实。

历史线索列表按时间早于目标检索；默认排除关键目标窗口，避免把事后样本当先兆。每条候选给出“何时、谁、触发何规则、对应事件、与目标相似/不同之处”。对“此前为何未引发明显行动”，提供同线程后续响应、外部压力轨和缺失记录供分析；没有记录不能解释成“没人注意”。

验收：同一候选可回查制度依据和具体命中片段；没有制度证据的规则显示“待确认预期”；至少完成一个有证据的历史对照，或输出可复核的“未找到足够证据”结论。禁止预置一个无法被事件支持的先兆来满足数量。

### M1-04 市场与压力轨作为第二层背景

市场图不是首个必做图。前面链路完成后，再接 market_by_round、environment_events、agents_unavailable 等数据，放在可折叠背景区。价格区分 source_snapshot、estimated_from_percent、forecast 等来源状态，预测不连接成历史真实价格线；没有观测点的时段不自动插值为事实。

压力、缺席和公开报道必须可回到 source pointer。情绪词表若展示，注明方法、未评分比例和文本来源，不能用股价跌落或情绪变化证明某 agent 的意图。验收以“能辅助查上下文且不篡改证据含义”为准，不以图表数量为准。

## 13. 通用比较面板：从相邻窗口倍数升级为可解释对照

### 13.1 第一版支持三种明确的对照方式

| 比较模式 | 选择方式 | 用途与约束 |
| --- | --- | --- |
| 手动历史窗 | 当前窗+用户选定的历史窗；可用“前一等长窗”快捷填入 | MC1/MC2 频率、渠道、对象分布；必须展示两个窗口完整端点 |
| 同角色/同主体 | 窗口内角色群组或同 actor 的既往记录 | 有可信角色元信息才开放同角色；控制组成变化，显示参与者数 |
| 匹配运行 | run_id+同 model/fixture 的正常 baseline_run_id | CUSTOM 流程比较，不以墙钟相邻运行代替匹配对照 |

前端 CompareView 增加模式选择、历史窗起止、覆盖与样本说明。CUSTOM 默认跳 RunCompare，避免用户把不同模型、任务、场景混在一个 2 小时窗口中得到无意义倍数。

当前窗和历史窗继承相同的非时间条件；在回放遮蔽下，当前窗截到游标，历史窗也不能包含游标之后的数据。若默认历史窗与当前窗相交，显示交集长度并要求调整；“前一等长窗”用 [a-(b-a),a) 与 [a,b)，无边界重复。

### 13.2 指标与分母写清楚

每行至少返回 window_count、baseline_count、window_share、baseline_share、rate、delta、ratio、is_new、evidence_filter。比例分母是该窗口相同筛选后的全部去重事件；当按 actor 比较且有 actor=null 时，保留“执行者未知”行，不能把它从总数消失。

每小时速率仅表示“请求窗口内平均记录率”。将窗口与数据可用范围相交得 exposure_range，同时返回 requested_duration、in_range_duration、observed_bucket_count、coverage_status。首末事件只能确定记录边界，不能证明中间持续监测；MC1 稀疏轮次数据 coverage_status=unknown，以“每已记录轮次消息数”等更合适指标为主。数据范围之外不得当成真实零活动参加速率计算。

基线 count=0 时 ratio=null，显示“本样本未出现”；两侧均 0 不画偏离；少于 5 条默认提示“小样本”，阈值可配置且不是显著性结论。新增/消失与 2 倍变化只作排序提示，删除所有可能暗示自动定罪的“异常率”用词。

### 13.3 比较结果必须能下钻

点击任一行的当前值/历史值，事件流分别载入该窗口和该项过滤，画布顶部显示“查看比较证据”及返回按钮。这个操作保存原比较状态，返回不丢历史窗。统计图 tooltip 给出原始数和分母，不能只给 2.3x。

验收：手工 SQL 与接口的两个窗口计数一致；窗口边界事件只落一侧；更换主体/关键词后比较结果同步变化；不完整观察范围不会显示成“历史完全没有这类行为”。

## 14. S5：案例恢复、结构化结论和导出

### 14.1 人工数据继续写独立 notes.db

保留现有 notes 及内容，不自动把旧自由文本拆成“事实”。新增 migration 只建新表，不清空历史笔记。建议最小 schema：

```sql
CREATE TABLE case_snapshots (
  case_id TEXT PRIMARY KEY,
  dataset_id TEXT NOT NULL,
  title TEXT NOT NULL,
  schema_version INTEGER NOT NULL,
  data_version TEXT NOT NULL,
  snapshot_json TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE TABLE findings (
  finding_id TEXT PRIMARY KEY,
  case_id TEXT NOT NULL,
  claim TEXT NOT NULL,
  status TEXT NOT NULL,
  explanation TEXT NOT NULL,
  limitations TEXT,
  intervention_json TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE TABLE finding_evidence (
  finding_id TEXT NOT NULL,
  dataset_id TEXT NOT NULL,
  reference_kind TEXT NOT NULL,
  reference_id TEXT NOT NULL,
  role TEXT NOT NULL,
  field_pointer TEXT,
  excerpt TEXT,
  source_hash TEXT NOT NULL,
  PRIMARY KEY (finding_id,dataset_id,reference_kind,reference_id,role)
);
```

reference_kind=event/context，context_id 用于 MC1 环境记录；role=support/counter/uncertain，status=hypothesis/supported/inconclusive。一个 finding 不允许混用不同 dataset 的 mini-challenge 证据；Design Challenge 的跨场景设计讨论另以报告章节组织。主库可重建，因此不建立跨库外键；创建引用时查主库，恢复时再次检查 source_hash 和引用可解析性。

### 14.2 状态快照要足以恢复分析

snapshot_json 至少保存 contract_version、FilterContext、canvasView、场景子模式、selectedEventId、focusedEntityId、selectedRunId、runPair、traceRoot、baselineSelection、固定证据列表；不保存 DOM 坐标、临时 tooltip 或正在播放状态。

恢复流程：先验证版本和数据集→检查 data_version→原子设置状态→加载数据→检查每个引用。数据版本不一致时显示 stale；允许查看旧结论和出处，但不把新数据查询结果当成原报告的证据。若明确进行重新验证，生成新的 snapshot 版本并记录变化。

预置案例放 backend/app/cases/*.json，并与人工案例使用同一验证器。GET /api/cases 合并返回只读预置案例和用户保存案例；用户“另存为”才写人工表。时间锚点仍是快捷筛选入口，不能把 anchor 自动当成完成了一个案例。

### 14.3 前端具体交互

新增 components/CasePicker.tsx、FindingEditor.tsx、EvidenceBasket.tsx。证据侧栏提供“加入证据篮”，可选支持/反证/待核实；FindingEditor 要求填写主张和解释，自动带入已选证据。自由笔记继续可用，用户可以主动转为结构化结论。

证据引用显示事件/背景 ID、时间、来源字段、短引文和数据版本。点击跳到记录时，若记录不在当前窗口，先显示“该证据位于当前筛选之外”，提供“定位并保留当前案例快照”；不能悄悄扩大筛选，造成统计上下文变化而无提示。

### 14.4 导出内容与验收

GET /api/cases/{id}/export?format=json 返回可恢复的机器格式；format=md 返回人可读报告，包含：调查问题、数据版本、实际筛选、图表说明、主张、支持证据、反证、未确定项、候选干预、来源索引。Markdown 引文全部做转义；后续转 HTML 时也需转义日志正文，不能执行原文中的标签或脚本。

首版截图由用户在案例状态下导出/保存，报告引用相对 assets 路径；不要为了做导出引入复杂服务端浏览器。S6 再用冻结案例生成三组图和主工程 submission/index.htm。报告只引用当前版本核验过的证据，内容缺失或候选关系明确写出。

验收：刷新浏览器后可恢复相同筛选、run pair、选中事件和固定证据；--fresh 重建主库后人工案例仍存在；旧版本引用标 stale；每个导出主张都有事件或 context 来源，空证据假设可以保存但必须显示“尚无证据”。

### 15.4 真实任务走查

### 16.3 每阶段实际运行的检查

下面给出 S1 以后完整检查的目标执行顺序。导入命令的参数、前端构建和颜色检查当前已存在，但 v2 表结构、backend/tests 和 bench_api.py 尚待实现；不能把下面整组命令描述为当前已经验证通过：

```powershell
# 从项目根目录构建临时 v2 库并核验；不直接覆盖正在使用的库
python -m backend.app.ingest.cli --all --db build/mas.v2.db --fresh

# 未来新增的准确性回归
python -m unittest discover -s backend/tests -v

# 当前已有的前端构建
npm --prefix frontend run build

# 当前已有的颜色检查
python tools/check_contrast.py --strict

# 启动后端，并确认其使用刚验收的库
$env:MAS_DB = (Resolve-Path build/mas.v2.db).Path
python -m uvicorn backend.app.main:app --port 8000
```

界面自检和 API 基准在服务运行后另一个终端执行：

```powershell
npm --prefix frontend run check:ui -- http://127.0.0.1:8000
python tools/bench_api.py --base-url http://127.0.0.1:8000 --samples 30
```

注意：当前 ui_check.mjs 以工作目录计算输出路径；用 npm --prefix 是否符合预期需随 UI-01 一并修正，建议脚本改为从 import.meta.url 定位项目 build。服务进程停止后再使用 S1 实现的替换流程提升新库为默认库；文档不能让用户一边运行服务一边删除其数据库。

### 16.4 阶段退出条件

一个功能只有满足以下四项才算完成：数据/接口可复核；从用户入口能完成操作；能回到对应原始证据；必需回归与该案例任务验收通过。只完成接口、只出现新标签、只展示预计算数字，均记为部分完成。

最终交付包含三条可恢复案例的 JSON、每条核心结论的来源索引、当前版本基准报告、已知缺口、安装/数据恢复说明、约 4 页设计说明草稿和演示脚本。MC2 正文缺失等不可闭合问题要进入交付限制，而不是隐藏在开发日志里。
