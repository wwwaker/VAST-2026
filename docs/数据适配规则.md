# 数据适配规则与字段映射

**配套文档：**《多智能体系统异常行为可视分析项目计划书》v1.2 第 8 章
**编制日期：** 2026-11-04
**版本：** 1.0
**用途：** 阶段 0 交付物。所有数据集差异在此收敛为 manifest 与 adapter 规则，前端组件内不出现 `if dataset === 'MC1'` 之类的字段猜测。
**核对方式：** 本文所有数字均为对 `data/processed/` 下实际文件的统计结果，不是计划书中的转述。

---

## 1. 结论摘要

三套数据的事件数、实体数、标签分布与计划书完全一致，可以直接开工。但字段层面存在 **16 处必须在 adapter 内处理、否则会静默产生错误结论**的问题，其中 5 处会直接影响演示能否跑通：

| 编号 | 问题 | 不处理的后果 |
| --- | --- | --- |
| C1 | MC1 `details.responding_to` 混装消息 ID 与 @提及文本 | 回复网络出现 266 条指向不存在事件的边，或整批丢失 |
| C7 | MC2 顶层 `timestamp` 是 UTC，`details.timestamp` 是本地墙钟（UTC−7） | 按官方"04:21"筛选得到空结果，目标帖子定位失败 |
| C9 | MC2 `task_label` 不是实体 ID | 造出 170 个不存在的任务节点，或全部 task 为 null |
| C10 | MC2 `parent_event_id` 全为空 | 链路重建按父子关系走会得到空图 |
| C13 | 自建数据没有 `source_record_id` 字段 | 可追溯性字段为空，违反成功标准 |

## 2. 规范层字段

规范层统一的是**可查询的基础概念**，不是把所有事件改写成同一业务含义。源字段永久保留在 `raw` 中。

### 2.1 事件

| 规范字段 | 类型 | 来源 | 说明 |
| --- | --- | --- | --- |
| `dataset_id` | string | manifest | 取值 `MC1` / `MC2` / `CUSTOM` |
| `event_id` | string | 源 `event_id` | 三套数据均全局唯一（912 / 185147 / 1103） |
| `source_record_id` | string | 源 `source_record_id` | **自建数据缺失，回落到 `event_id`**，并在 `raw_ref.missing_source_record_id = true` 标记 |
| `timestamp_raw` | string | 源 `timestamp` | 原样字符串，不做任何改写 |
| `timestamp_normalized` | string | 派生 | MC1 保持朴素源时间字符串；MC2 统一 `Z` 结尾；CUSTOM 保持 `+00:00` |
| `timezone_status` | enum | manifest | `unknown`（MC1） / `utc`（MC2、CUSTOM） |
| `time_sort_key` | string | 派生 | MC1 用源时间朴素键；MC2/CUSTOM 用 UTC epoch。**禁止跨数据集比较** |
| `actor_id` | string \| null | 见 §4 | MC2 有 322 条为空，不得臆造 |
| `participant_ids` | string[] | 见 §4 | 由 `party_ids` / `recipients` / `relationships` 合并去重 |
| `event_type` | string | 源 `event_type` | 按 manifest 的类型字典给出中文标签与类别色 |
| `task_id` | string \| null | 源 `task_id` | 仅自建数据有值；MC1/MC2 恒为 null，**不得用 `task_label` 填充** |
| `document_id` | string \| null | 源 `document_id` / `file_id` | MC2 用 `file_id`（51,402 条，100% 可解析到实体）；自建数据 100% 有值；MC1 恒为 null |
| `parent_event_id` | string \| null | 源 `parent_event_id` | MC1 483 条、自建 1,039 条；**MC2 恒为 null** |
| `relationships` | object[] | 源 `relationships` | 原样保留，另存派生边 |
| `details` | object \| null | 源 `details` | 结构因类型而异，详情面板按类型渲染 |
| `raw_ref` | object | 派生 | `{ file, json_pointer, round_hour }` |
| `annotations` | object[] | 标签文件 / 人工 | 见 §6 |

### 2.2 实体

统一字段：`dataset_id`、`entity_id`、`entity_type`、`source_value`、`label`、`roles[]`、`attributes`、`raw_ref`。

三套数据的实体容器路径不同，由 manifest 声明：

| 数据集 | 容器 | 实体数 | 结构差异 |
| --- | --- | ---: | --- |
| MC1 | `entities.json` → `entities[]` | 13 | 有 `roles[]`、`labels[]`；无 `attributes` |
| MC2 | `entities.json` → `entities[]` | 15,538 | 有 `org_edges[]`（74 条）；无 `roles` |
| CUSTOM | `entities.json`（**根即数组**） | 330 | 属性直接平铺在实体上，键集合有 6 种 |

CUSTOM 的实体属性不固定，必须整体塞进 `attributes`：

- actor 有 2 种形态：160 条含 `model` + `thread_id`，32 条（controller）不含
- `document_version` 42 条带 `sha256` + `version`，这是版本传播类异常的核心证据
- `task` / `document` / `file` 各 32 条，分别只有 `state` / `format` / `path`


### 4.2 MC2（185,147 事件 / 15,538 实体 / UTC）

| 源字段 | 规范字段 | 规则 |
| --- | --- | --- |

### 4.3 CUSTOM（1,103 事件 / 330 实体 / 32 run / UTC）

时间范围 `2026-11-03T08:07:24` → `2026-11-03T08:20:32`，全部 32 次运行集中在 13 分钟内。`task_id`、`document_id` 100% 有值。

| 源字段 | 规范字段 | 规则 |
| --- | --- | --- |
| `event_id` | `event_id` + `source_record_id` | 无 `source_record_id`，回落到 `event_id`，见 C13 |
| `parent_event_id` | `parent_event_id` | 1,039 / 1,039 全部可解析 |
| `version` | `attributes.version` | 456 条为 null，是版本类异常的判据之一 |

## 5. 冲突与歧义规则

### C1. MC1 `responding_to` 是双语义字段

**实测：** 749 条有值，483 条是消息 ID（匹配 `source_record_id`），**266 条是 `"@legal @pr @platform_trust"` 这类提及文本**（one_on_one 131、side_huddle 98、broadcast 37）。

**规则：** 按值形态分流。能匹配到消息的生成 `reply_to` 边（有向，来源=源字段）；含 `@` 前缀的分词生成 `mention` 边（有向，指向角色）。二者在界面上必须视觉区分——提及不是回复。无法判定的写入 `unresolved_refs`，在详情面板显示"未解析的引用"，不静默丢弃。

**验收：** 回复边 483 条、提及边 266 条、`unresolved_refs` 为 0。

### C2. MC1 同时存在两套 ID 空间

`parent_event_id`（483 条）全部指向规范 `event_id`（`MC1:event:...`），而 `responding_to` 指向 `source_record_id`（`20460605_22_003`）。

**规则：** 导入时建立 `source_record_id → event_id` 映射表并在 adapter 内完成转换。规范化结果中，所有引用字段统一存放 `event_id`。

**补充（建库后校正）：** 这类「指向另一条事件」的关系边必须显式标记 `target_kind='event'`，
否则关系图会把事件 ID 当成实体节点画出来。实测 MC1 未区分时，图上多出 8 个 `unknown` 类型的伪节点。
关系图的查询一律加 `AND target_kind='entity'`。

### C3. MC1 收件人短名有 1 个无法解析

`raw.recipients` 共 903 个 token：`ALL` 488、`pr` 151、`platform_trust` 97、`social_manager` 77、`legal` 63、`pr_intern` 21、`intern` 5、`judge` 1。

**实测：** 除 `ALL` 外，唯一无法映射到任何 agent 角色的是 **`social_manager`**——实际实体是 `social_media_agent`（role=`social_media`，label=`Social-Manager-Agent`）。

**规则：** manifest 内维护显式别名表 `{ "social_manager": "MC1:agent:social_media_agent" }`。`ALL` 不生成指向实体的边，而是标记为"频道广播"，收件人为该 channel 全体 agent。**禁止用模糊字符串匹配兜底**，否则 `pr` 会误配到 `pr_intern`。

### C4. MC1 的收件关系分两套来源

**实测（建库校正）：** `relationships` 在 230 条事件上有值，共 **415 条边，关系名统一为 `recipient`**，且**只出现在 `one_on_one_chat`（131 条）与 `side_huddle`（284 条）**。`broadcast`（388 条）与 `public_post`（77 条）的 `relationships` 一律为空，收件人只存在于 `raw.recipients`。

**规则：** 两套来源合并为 `participant` 的 `recipient` 角色，但必须保留 derivation 区分：

- 来自 `relationships` 的边记为 `source:relationships`，属于原始观测；
- 来自 `raw.recipients` 的收件人记为 `adapter:recipients`，属于规范化解释。

界面与 API 都要能区分这两类，不能一律表述为"源记录中的收件关系"。广播消息的 `ALL` 单独记为 `broadcast_audience` 角色，不与具体收件人混为一谈。

### C5. MC1 双声道覆盖率只有 9.4%

`raw.internal_state` 非空仅 **86 / 912**：`deliberating` 61、`reacting` 19、`rationalizing` 6。按类型分布：broadcast 76、one_on_one_chat 9、public_post 1。

**规则：** 双声道对照只在有审议文本时展示；无文本时右声道显示明确空状态（"该事件无内部审议记录"），不渲染空面板。演示脚本选取的锚点事件必须落在 86 条之内。`internal_state` 三个字段分别标注来源，结论不得单凭审议文本定性。

### C6. MC1 时区未知，且轮次时间与事件时间不同

事件时间到分钟（`18:55`），`round_hour` 是轮次起点（`18:00`）。

**规则：** 时间泳道横轴用 `timestamp`；回放推进按 `round_hour` 分组，避免在 55 分钟间隔里空转。所有绝对时刻在界面上带"源时区未知"文字标签。

### C7. MC2 双时间戳相差 7 小时

**实测：** 225 条帖类事件的顶层 `timestamp` 与 `details.timestamp` 相差 6.9–7.1 小时，稳定偏移。

**验证：** 官方描述的目标帖"2046-05-17 04:21"对应文件中 **`2046-05-17T11:21:15Z`（`MC2:event:373902`）**。即顶层是 UTC，`details.timestamp` 是 UTC−7 的本地墙钟。

**规则：** 排序、筛选、聚合一律用顶层 `timestamp`；`details.timestamp` 只在证据面板中作为"来源本地时间"展示。锚点在 manifest 中存 `utc` 与 `source_local` 双值，界面同时显示。

### C8. MC2 同一业务行为产生成对记录

| 行为 | 平台记录 | 动作记录 | 数量 |
| --- | --- | --- | --- |
| SaidIT 发帖 | `saidit_post` 108 | `post_saidit` 156 | 不成对，108 vs 156 |
| FleX 发帖 | `flex_post` 120 | `post_flex` 156 | 不成对 |
| 邮件 | `sent` 7407 / `received` 7266 | `send_email` 45 | 三份不同口径 |

**规则：** `type_dictionary` 增加 `is_record` 布尔位，区分"动作事件"与"平台回执事件"。任何"事件数"统计必须声明口径；`time_buckets` 预聚合时按 `is_record` 分组，默认趋势图只用动作记录，否则发帖量会翻倍。

### C9. MC2 `task_label` 不是任务实体

57,636 条非空，170 个去重值，**0 个能匹配实体 ID**。取值混杂三种语义：事件类型名（`virus` 30,101、`access_email` 7,891）、派生任务名（`Work-Order Triage for Maintenance Requests` 405）、流程标签（`general operations: ... follow-up`）。

**规则：** 不写入规范 `task_id`，整体进 `attributes.task_label`。仅在按标签筛选时作为文本条件使用。`task_id` 保持 null。

### C10. MC2 没有父子事件链

`parent_event_id` 185,147 条**全为 null**。

**规则：** 链路重建不能依赖父子关系。MC2 的链路来源限定为：`party_ids` 交集、`mail_sender`/`mail_recipient` 配对、`queue_target_person` → 后续 `agent task`、`post_content_source` 指向的文件实体、以及时间邻近。每条链路边都要标注推导方式与置信说明。

### C11. MC2 的 actor 是推导出来的

322 条 `actor_id` 为 null。非空值由 `actor_rule` 推导：`sole_party` 82,274、`sole_agent_party` 63,472、`queue_owner_or_non_target_agent` 16,716、`details.from` 7,452、`details.name` 7,420、`details.to` 7,266、`details.poster_id` 225。

**规则：** `actor_rule` 必须随事件一起返回，并在证据面板显示"actor 由 sole_party 推导"。这类 actor 属于**规范化解释**，不得与原始记录里的显式字段等同表述。
**补充（建库实测）：** 322 条 actor 为空的事件中，有 **38 条仍带关系边**。因此 `relations.src_id` 必须允许为空，`derivation` 记为 `source:relationships:actor_null`，不得为了凑出源节点而臆造 actor。

### C12. MC2 关系图默认不可读

`file_path` 实体占 98.5%；91,619 条（49.5%）事件没有任何 `relationships`。

**规则：** 默认图只含 `agent` / `person` / `system` / `team` / `department` 五类节点，`file_path` 与 `room` 需显式勾选才出现；节点上限按视口设定，超出时提示"已完成裁剪"而不是静默截断。

### C13. 自建数据没有 `source_record_id`

事件键集合固定为 11 个字段，不含 `source_record_id`。

**规则：** `source_record_id = event_id`，并在 `raw_ref` 标记该回落。可追溯性验收时，自建数据的"来源记录 ID"即事件 ID 本身。

### C14. 自建数据同类型多形态

见 §4.3。详情面板采用"已知字段优先渲染 + 其余字段按原始 JSON 展开"策略，不能对每种 `event_type` 写死模板。

### C15. `scenario` 与 `observed` 必须分离

32 条标签：`normal` 8（全 false）、`bypass_review` 8（全 true）、`repeated_handoff` 8（全 true）、`stale_version` 8（**5 true / 3 false**，false 的 reason 为"观察到旧版读取，未核实旧版已传播"）。

**规则：** 三态展示：未配置异常 / 配置为异常且观测到 / 配置为异常但未观测到。第三种必须显示 reason 原文，不能被渲染成"正常"。

### C16. `target_id` 为空不等于无关系

MC1 775 / 912 为空、MC2 140,024 / 185,147 为空、CUSTOM 424 / 1,103 为空。

**规则：** 参与者一律从 `participant_ids` 读，`target_id` 只作为"显式目标"的一个可选来源。界面不得把 `target_id` 为空表达为"无交互"。
