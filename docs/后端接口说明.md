## 1. 结构

```text
backend/
  requirements.txt
  app/
    config.py             路径与库位置（MAS_DB 可覆盖）
    db.py                 每请求一个只读连接
    main.py               FastAPI 装配；构建后由它托管 frontend/dist
    ingest/
      manifest.py         三数据集的全部差异（时区、实体容器、锚点、收件人别名）
      schema.py           表与索引
      loader.py           adapter：字段映射、关系派生、校验
      cli.py              导入命令行
    routers/
      datasets.py         /api/datasets、/api/datasets/{id}/overview
      events.py           /api/events、/api/events/{event_id}
      entities.py         /api/entities、/{id}/events、/{id}/neighbors
      search.py           /api/search
```

导入与查询完全分离：`python -m app.ingest.cli` 只写库，服务启动时不重新导入。

## 2. 导入

```bash
cd backend
python -m app.ingest.cli --all --fresh      # 全量重建
python -m app.ingest.cli --dataset MC1      # 只重导一个
```

实测结果（本机，`build/mas.db` 248 MB，总计约 20 s）：

| 数据集 | 事件 | 实体 | 参与者 | 关系 | 全文索引 | 耗时 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| MC1 | 912 | 13 | 1,322 | 2,709 | 912 | 0.16 s |
| MC2 | 185,147 | 15,538 | 346,503 | 147,901 | 125,651 | 15.4 s |
| CUSTOM | 1,103 | 330 | 1,782 | 0 | 412 | 0.22 s |

导入结束会打印校验项，任一失败则退出码非 0：

- 小时聚合、概览统计是否生成
- MC1 时间是否未被转换成 UTC
- 每个锚点在 ±1h 内能否定位到事件
- 自建集 165 个 `affected_event_ids` 是否全部可解析

**关系边的口径**（与文档 C1–C16 对应）：

| 来源 | derivation | target_kind | 数量（MC1） |
| --- | --- | --- | ---: |
| `responding_to` 命中消息 ID | `adapter:responding_to` | `event` | 483 |
| `responding_to` 是 @提及文本 | `adapter:mention_text` | `entity` | 411 |
| `relationships` 原生边 | `source:relationships` | `entity` | 415 |
| 频道归属 | `source:channel_id` | `entity` | 912 |
| `raw.recipients` 含 `ALL` | `adapter:recipients` | `entity` | 488 |

不存在的关系边一律不建；MC2 有 38 条关系边的源事件 `actor_id` 本身为空，`src_id` 保持 null。

`target_kind` 区分「指向实体」与「指向另一条事件」。前者可以进关系图，后者只能进时间线。
建库后 MC1 为 2,226 条实体边 + 483 条事件边，MC2 全部为实体边。

## 3. 接口

所有接口都要求 `dataset` 参数，避免跨数据集误用时间轴（MC1 时区未知）。

### GET /api/datasets

数据集体量、时区状态与锚点。锚点直接取自 manifest，不落库，改配置后重启即生效。

```json
[{ "dataset_id": "MC2", "event_count": 185147, "timezone_status": "utc",
   "anchors": [{ "key": "target_post", "label": "目标帖子 11:21Z",
                 "sort_key": 2410168875, "timezone": "utc", "note": "…" }] }]
```

### GET /api/datasets/{id}/overview

参数：`granularity=day|hour`、`top_types=1..24`、`start`、`end`。

返回的 `series` 与前端渲染用的格式一致，超出 `top_types` 的类型合并为 `__other__`：

```json
{ "series": { "types": ["check_email", "…", "__other__"],
              "buckets": [2410…, …],
              "points": [[bucketIndex, typeIndex, count], …] },
  "types": [{ "type": "check_email", "count": 37286 }],
  "actors": [{ "entity_id": "MC2:agent:…", "label": "…", "count": 30206 }] }
```

### GET /api/events

参数：`dataset`、`start`、`end`、`types`（逗号分隔）、`actor`、`q`、`limit`（≤500）、`cursor`、`direction`。

时间+ID 稳定游标：`cursor` 取上一页的 `next_cursor`（形如 `<time_sort_key>|<event_id>`），
分页不会因新事件插入而重复或跳漏。返回项含 `preview`、`has_deliberation`、`annotations`。

### GET /api/events/{event_id}

详情 + `raw` + 参与者 + 关系边 + 标注。**同时接受 `source_record_id`**——
MC1 的 `responding_to` 和官方记录 ID 都是这个口径，用错也不会 404。

双声道相关字段：

| 字段 | 含义 |
| --- | --- |
| `outgoing_text` | `details.content`，左声道 |
| `deliberation` | `raw.internal_state` 中非空的 `reacting` / `rationalizing` / `deliberating`，右声道 |
| `deliberation_source` | 固定为 `raw.internal_state`，无内容时为 null |

`/api/events` 另支持 `has_deliberation=true`，用于只筛出含内部审议的事件；`/api/datasets`
与 `/api/datasets/{id}/overview` 返回 `deliberation_count`，供界面提示覆盖率（MC1 为 86 / 912）。

### GET /api/entities、/api/entities/{id}/events、/api/entities/{id}/neighbors

实体列表带类型分布；时间线用 `participants.time_sort_key` 排序，不回表；
邻接为双向各限流一次再在应用层合并（查询期不做 `GROUP BY`）。

### GET /api/graph

参数：`dataset`、`center`（实体 ID）、`depth=1|2|3`（默认 2）、`node_limit≤80`。

返回 `nodes`（含 `entity_type`、`degree`、`is_center`、可读 `label`、距中心的 `level`）与 `edges`
（含 `relation`、`derivation`、`evidence_count`）。服务端硬限流：每跳最多 10 个种子、
每种子每方向 25 条边、总节点 80、总边 300，超限返回 `truncated=true`。

**只返回 `target_kind='entity'` 的边。** MC1 的 483 条 `reply_to` 指向的是另一条事件，
不是实体；若不区分，关系图会把事件 ID 当成节点画出来（实测出现过 8 个 `unknown` 类型的伪节点）。

实体名在服务端解析：优先 `label`，否则从 `source_value` 取最后一段并把下划线换成空格
（`Agent/person:zoey_drydock` → `zoey drydock`）。

| 场景 | 实测 |
| --- | ---: |
| MC2 `john_windward` / 1 跳 | 18 节点 · 20 边 · 95 ms（首调） |
| MC2 `john_windward` / 2 跳 | 60 节点 · 133 边 · 34 ms |
| MC1 `social_media_agent` / 1 跳 | 6 节点 · 8 边 · 18 ms |

### GET /api/compare

参数：`dataset`、`start`、`end`（当前窗口，epoch 秒）、`baseline_start`、`baseline_end`
（留空则自动取等长的前一个窗口）、`dimension=event_type|actor`、`limit`。

返回两个窗口的事件数与逐项计数，并统一折算为**每小时速率**：

```json
{ "window":   { "start": 2411..., "end": 2411..., "hours": 2.0, "events": 101 },
  "baseline": { "start": 2411..., "end": 2411..., "hours": 2.0, "events": 98, "auto": true },
  "rows": [{ "key": "public_post", "window_rate": 7.0, "baseline_rate": 2.0,
             "delta": 5.0, "ratio": 3.5, "is_new": false, "is_absent": false }] }
```

必须按速率而不是绝对数比较：窗口长度不同时，长窗口永远显得更异常。
`ratio=null` 表示基线窗口内该类事件为 0，界面显示为"新增"，不给无限大的倍数。

实测：MC2 按 actor 比较 16.6 ms；MC1 按 event_type 比较 57 ms（首次调用含预热）。

用 MC1 的 17:25 锚点窗口（16:25–18:25，101 条）对比前一个等长窗口（14:25–16:25，98 条），
`public_post` 从 2.0/h 升到 7.0/h（3.5x）——这正是解禁前那段窗口的行为特征。

### /api/notes

调查笔记，支持列表、新建、删除。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/notes?dataset=MC1` | 按数据集列出，新的在前 |
| POST | `/api/notes` | body：`dataset_id`、`body`、可选 `event_id`/`event_time`/`filter_summary` |
| DELETE | `/api/notes/{note_id}` | 成功返回 204 |

**笔记单独存在 `build/notes.db`，不放进 `mas.db`。** 导入命令的 `--fresh` 会删除整个
`mas.db` 文件，若笔记混在里面，一次重建就全没了。实测：写入笔记后执行
`python -m app.ingest.cli --all --fresh`（11.5 s，全部校验通过），笔记与内容原样保留。

笔记按 `dataset_id` 隔离，MC1 的笔记不会出现在 MC2 列表里。空内容返回 400，
未知数据集返回 404。笔记属于人工结论，不参与事件检索，也不随数据标签变化。

### GET /api/search

FTS5 检索。返回 `ordered_by: "index_hit_order"`，即**未做相关性排序**——
`ORDER BY bm25()` 在本数据量上会把响应从 30 ms 拖到秒级，界面按时间倒序展示更实用。

### /api/files、/api/file-track（仅 MC2）

文件按实体 `file_path` 的**完整路径**区分，同名不同路径分别列出，不按 basename 合并。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/files?dataset=MC2&q=SwiftWren` | 候选文件：`file_id`、`path`、`event_count`、`first_us`/`last_us`、`exact` |
| GET | `/api/file-track?dataset=MC2&file_id=...` | 文件轨迹：事件分页 + `relation_counts` + `file.content_status` |

`file-track` 复用统一 `FilterContext`（时间窗、actor、关键词、游标遮蔽），返回的
`meta.matched_events` 与事件流的计数口径一致。`file.content_status` 三态：

- `available`：至少一条关联事件的 `details` 含正文级文本（会给出 `event_id` + 字段名）；
- `metadata_only`：只有文件名、动作或 `size_hint`，**界面必须显示“仅有元数据”**；
- `unresolved`：文件实体存在但没有任何可解析事件。

### /api/traces、/api/traces/roots（仅 MC2）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/traces/roots` | 带 `post_content_source` 的发布事件（当前 3 条），作为链根候选 |
| GET | `/api/traces?root_event_id=...` | 记录层 + 候选层 + 预算与裁剪原因 |

边的 `provenanceKind`：

- `recorded`：载荷或 `relations` 直接给出，`evidenceEventIds` 非空；
- `candidate`：只表示文件名前缀相同（`ruleId=shared_prefix_hint`），
  `evidenceEventIds` 为空，不计入 `recorded_edge_count`。

根事件晚于回放游标时返回 **409 `root_after_cursor`**，不把未来事件当作当前已知。
`budget.truncated=true` 时同时给出 `reasons`（目前只有 `event_budget`）。

`tools/audit_mc2_content.py` 生成 `build/mc2-content-audit.json`，记录内容可用性、
正文字段扫描、官方包成员清单，以及“可支持/不可支持”的结论边界。

### /api/patterns/file-posts、/api/interventions（仅 MC2）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/patterns/file-posts?before_us=` | 以文件为内容源的发布实例，7 阶段签名 + `matched_stages` / `missing_stages` |
| GET | `/api/interventions?position=relay_queue` | 单点干预：覆盖、附带影响、切断分析、局限 |

7 个阶段：`content_created`、`instruction_read`、`relay_queued`、`pre_post_receipt`、
`posted`、`cleanup_instruction`、`cleanup_content`。阶段存在性由事件决定；
`content_file` 与 `instruction_file` 的对应关系来自**文件名前缀**，响应里用
`link_basis="name_prefix"` 标注，不能当作记录关系。

`relay_queued` 只返回 `total`（如 186 次）、`nearest_event_id` / `nearest_actor` /
`nearest_lag_us`（发布前 60 秒内最近一次）和 10 条样本，不把上百个事件整列返给前端。

`interventions` 的 `coverage_summary` 区分完整链与部分链；`impact` 给出排队任务总数、
带 `queued_file_path` 的条数（235）与目标文件条数；`cut_analysis.deterministic_path_exists`
为 false 时界面必须显示“无法对确定路径做切断证明”。

### /api/cases、/api/findings（案例、结论与导出）

预置案例来自 `backend/app/cases/custom.json`（只读）；用户案例与结论写入独立的
`notes.db`，主库 `--fresh` 重建不会带走它们。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/cases?dataset=CUSTOM` | 预置案例 `items` + 用户案例 `user_items` |
| POST | `/api/cases` | body：`dataset_id`、`title`、`snapshot`；返回 `case-xxxxxxxx` |
| GET | `/api/cases/{case_id}` | 预置或用户案例 + 已有结论 |
| DELETE | `/api/cases/{case_id}` | 只删用户案例；预置案例返回 400 |
| GET | `/api/cases/{case_id}/export?format=json\|md` | 导出；`Content-Disposition` 直接下载 |
| POST | `/api/findings` | body：`case_id`、`claim`、`status`、`explanation`、`evidence[]` |
| GET | `/api/findings?case_id=` | 按案例列出结论 |
| DELETE | `/api/findings/{id}` | 删除结论及其证据行 |

`snapshot` 只保存恢复分析所需的状态（`filters`、`canvas_view`、`selected_event_id`、
`focused_entity_id`、`trace_root_id`、`pinned_evidence`），不保存 DOM 坐标或播放中间态。

`findings.evidence[]` 的 `reference_id` 必须是该案例数据集里存在的事件；不存在时返回
400 并列出 ID，不会写入半条结论。`source_hash` 由服务端按
`dataset|event_id|timestamp_raw|details_json` 计算，用于判断“结论基于的证据是否被换过”。

导出 JSON 是可恢复的机器格式；导出 Markdown 依次给出恢复状态、冻结案例、每条结论
（主张/状态/解释/局限/证据表/反证）、未解析项与方法限制。所有正文按 HTML 转义后再进表格。

状态判定三层，任何一层不符都返回明细而不是换一组运行：

1. **运行与配对**：`run_id` / `baseline_run_id` 是否存在、模型与 fixture 是否一致、
   `run_pairs` 里是否真有这条配对；
2. **期望值**：逐项对照 `custom_audit.audit_run` 的重算结果，差异写入 `diffs`
   （`status=mismatch`）；
3. **数据版本**：文件里的 `data_version` 与当前 `datasets.data_version` 不同时，
   整组标 `stale`，原判定保留在 `computed_status`。

`evidence` 里冻结的 `attempt` / `review` / `publisher_read` / `result` / `handoff_*`
会在详情接口里解析成事件；解析不到时该项 `missing=true`，不会静默丢弃。

### /api/system-overview、/api/system-overview/members（仅 MC2）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/system-overview?trace_root_id=` | 类型级聚合 + 交互边 + 静态组织边 + 目标事件高亮 |
| GET | `/api/system-overview/members?entity_type=agent&limit=20` | 展开某个类型，返回真实 `entity_id` |

15,538 个实体聚合成 9 组（`group:agent`、`group:file_path` 等），外加一个
`group:unknown` 表示关系端点无法解析（当前 0 个端点 / 19 条事件）。聚合节点用
`group_id`，**不是**源实体；`member_count` 与 `participation_count` 分开，
后者是参与次数，同一事件里有多个同类型参与者会各计一次。

交互边按 `(源类型, 目标类型, 关系)` 去重计数（当前 15 条，如 agent→file_path 51,399）；
`sample_event_id` 只是下钻样本，不是“最早事件”。组织边（74 条 `contains`/`led_by`）
来自 org_chart，`temporal_status=static`，没有时间戳。

首屏聚合要扫全量参与者与关系，因此按数据库文件状态做进程内缓存，响应里
`meta.cache_hit` 标明是否命中；展开成员走独立接口，避免重复计算整张地图。

## 5. 踩过的坑（都在代码注释里标了）

| 问题 | 现象 | 根因 | 处理 |
| --- | --- | ---: | --- |
| 事件详情 1,133 ms | 单条详情要 1 秒 | `relations` 缺 `(dataset_id, event_id)` 索引，147k 行全表扫 | 建 `idx_rel_event` → 9 ms |
| 检索 1,381 ms | 关键词查询要 1.4 秒 | `snippet()` 对每个命中行重新切词 | 去掉，改在应用层截取上下文 → 29 ms |
| 检索仍 1,080 ms | 去掉 snippet 后仍慢 | FTS 直接 JOIN `events` 时规划器退化成 `SCAN events`（每次命中扫 18 万行） | 先取 rowid，再按主键批量回表 |
| 概览 547 ms | 按天概览要半秒 | 活跃主体用 `GROUP BY` 扫 18 万行 | 改读导入期的 `stat_counts` → 18 ms |
| 切换数据集空结果 | 切到自建集显示 0 条 | 沿用了 MC2 的时间窗，两套时间轴不可比 | 切换时清空筛选与选中，并在状态条提示"无筛选" |

## 6. 已知限制

- **未做并发压测**：基准为单进程单连接。WAL 支持多读一写，多 worker 需另行验证。
- **检索无相关性排序**，只按索引命中顺序返回；同一关键词在 80,712 条事件正文里出现时，前 50 条不一定是"最相关"的。
- **两跳邻接未实现**，递归 CTE 的规模与延迟未测。
- **CUSTOM 的关系边为 0**：源数据本身没有 `relationships`，父子关系仅存于 `parent_event_id` 列，尚未转成边。
- **缺少写接口**：调查笔记目前只在前端内存中，刷新即丢失。
